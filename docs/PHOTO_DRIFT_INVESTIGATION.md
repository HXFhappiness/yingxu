# 照片回放帧间漂移：可复现的候选原因

本调查基于统一分支 `0f92aac`；生产照片/视频 RTL 没有修改。字模资产另由
`fix/menu-font` 的 `4634b5c` 原样引入，未引入该分支较早的顶层控制代码。

## 现象与候选修法

`yingxu_sdram_video_player` 在每帧垂直消隐开始时拉高 `rd2_load`，重新设置
SDRAM 读地址，但 `yingxu_sdram_control_4port` 只有在 `MJ_ACTIVE=1` 时才用
`RD2_LOAD` 清读 FIFO。照片模式下，地址已经重置，FIFO 中的预取数据仍会
继续输出；地址与队列不再表示同一个帧起点。

低影响候选改动只有两个位置：

1. 照片的 `RD2_LOAD` 同时复位读 FIFO。
2. 照片消隐期 LOAD 从约 8 个像素时钟延长到约 256 个，约 3.45 微秒。
   控制器在 LOAD 期间不启动新事务，已发出的 128 字突发可以完成并被丢弃；
   随后从帧首填充干净的队列。只加清 FIFO 而不延长保持时间，可能混入
   复位前在途突发的尾部。

不需要逐行重载、修改 PLL、修改 HDMI 时序或改变 SD/BMP 解码路径。
这些改动目前只由验证脚本生成到 `out/photo_phase_check/`，没有合入生产 RTL。

## 复现方法与证据

```sh
python3 tools/photo_phase_verify.py
```

脚本分别编译生产 RTL 和临时候选副本。测试使用实际照片回放、四口 SDRAM
控制器与原生 1280×720 / 1650×750 光栅，FIFO、PLL、SDRAM 存储单元使用
既有功能模型。每个 SDRAM 字带唯一标签；记录首个完整活动帧，再比较后续
五帧的所有 2,304,000 对像素。首次 LOAD 特意与真实控制器的在途读重叠。

生产版本要求复现帧间不一致，候选版本要求逐字一致并确实覆盖在途读。
原始日志与源码 SHA256 存放在 `docs/evidence/PHOTO_PHASE/`。

这是帧间相位验证，不是 SDRAM 引脚时序或完整 RGB 色彩验证；模型中的突发
边界数据延迟不作为绝对像素金标准。仿真复现了队列与地址失配，但没有复现
或解释板上“约 3 px/s”的精确速率。候选方案仍需照片切换、视频进出回归、
TD 时序和真机静态照片长时间观察，才能认定解决了板上同一问题。
