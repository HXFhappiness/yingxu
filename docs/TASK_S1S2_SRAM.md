## 2. 方案 A：板载 SRAM 512 KB 双用途（码流预取 + PCM 缓冲）

### 2.1 硬件依据（已实测核实，非假设）

| 项 | 数据 | 出处 |
|---|---|---|
| 芯片 | IS61WV25616EDBLL-10TLI，256K×16 = **512 KB**，10 ns 异步 | 原理图 + `AC201_AL_SRAM/sram.md` |
| **现成控制器** | `YX-tool/AC201_AL_SRAM/rtl/sram_async_ctrl.v`（204 行） | 随板参考工程，已完成 |
| 控制器接口 | `cmd_valid_i/cmd_write_i/cmd_addr_i/cmd_wdata_i/cmd_byte_en_i` → `cmd_ready_o/rsp_valid_o/rsp_rdata_o` | 同上（标准 ready/valid，可直接挂载） |
| 访问时序 | 写 4 拍（SETUP→PULSE→HOLD→DONE）；读 4 拍（SETUP→WAIT→CAPTURE→DONE） | 同上 |
| **有效带宽** | 50 MHz / 4 拍 × 2 B = **25 MB/s** | 由上一行推出 |
| 引脚 | **39 个专用**（18 地址 + 16 数据 + CE/OE/WE/LB/UB） | `AC201_AL_SRAM/IO.adc` |
| **引脚冲突** | 与主工程实际在用 38 引脚**零冲突**（仅 clk/uart 复用同一引脚，属正常） | 本次逐脚比对，结果见附录 A |
| 现成验证资产 | `tb/sram_async_model.v`、`tb/tb_sram_bist_top.v`、`tb/tb_sram_uart_top.v`、BIST 引擎、UART 桥 | 随板参考工程 |

**为什么 25 MB/s 够（而它看起来不够快）**：视频码流只要 **0.72 MB/s**（30 KB/帧 × 24），
PCM 只要 **0.19 MB/s**，合计 0.91 MB/s —— 25 MB/s 有 **27 倍余量**。
SRAM 的定位是**小容量、低延迟、抗抖动**，不是大带宽搬运；这正是我们缺的那一环。

### 2.2 分区设计（512 KB = 524,288 B）

| 区 | 容量 | 内容 | 缓冲深度 |
|---|---:|---|---|
| A. JPEG 码流环形缓冲 | 384 KB（0x00000–0x5FFFF） | 已校验的整帧 JPEG 字节 + 帧边界描述符 | **12 帧 @32 KB** 或 15 帧 @25 KB |
| B. PCM 环形缓冲 | 64 KB（0x60000–0x6FFFF） | 裸 PCM（由 pcm_bridge 转虚拟 YXMA 喂 WAV） | **341 ms** @192 KB/s |
| C. 备用 | 64 KB（0x70000–0x7FFFF） | 复赛：纹理/精灵图集、调试快照 | — |

**关键收益 1：BRAM 从 19 块降到 15 块**
原设计 PCM reservoir 占 4 块 BRAM（4096×8）。搬到 SRAM 后 BRAM 目标降为 **15 块**，
总计 39+15 = **54/64，留 10 块余量**（复赛菜单/纹理才有空间）。

**关键收益 2：SD 抖动被完全吸收**
12 帧 × 32 KB 缓冲 = **480 ms 视频**。即使 SD 卡因内部 GC 卡顿 400 ms，播放不中断。
这是把验收口径从"瞬时速率"改为"平均速率"的物理基础。

### 2.3 接口与仲裁设计约束

- SRAM 只有**一组**物理接口：必须做 2 路（A 码流写、B PCM 写）+ 2 路读（A 解码消费、B WAV 消费）的仲裁。
- 建议策略：**按帧边界优先级仲裁**，不做逐拍轮转——
  - 写侧：PCM 低水位优先（每次最多 4 扇区），否则 JPEG 写；
  - 读侧：JPEG 解码读一旦发起就**连续读完一个 MCU 组**（不允许半途切走），PCM 读插在其间隙。
  - 理由：SRAM 25 MB/s 相对需求有 27 倍余量，仲裁只需保证**不饥饿**，不需要精细调度。
- 所有跨时钟域（`sys_clk` 50 MHz 单域即可，SRAM 控制器本身就在 50 MHz）统一用 held-bus + toggle 确认，不要多比特直通。
- **不得改动** `sram_async_ctrl.v` 的状态机时序（那是已验证的 10 ns 器件时序）。

### 2.4 实施步骤（S2-A）

| 步 | 内容 | 判据 |
|---|---|---|
| A1 | 把 `sram_async_ctrl.v` + `sram_async_model.v` 复制进 `src/user_source/hdl_source/media/sram/`（不改内容，仅迁入） | 原有 `tb_sram_bist_top.v` 在新位置跑通 |
| A2 | `IO.adc` 增加 39 条 SRAM 引脚约束（从参考工程 `IO.adc` 抄，逐条核对） | TD 打开无引脚重复报错；**照片/音乐/卡带三路功能不变**（回归） |
| A3 | 写 `sram_ring_buf.v`（环形缓冲 + 描述符，独立可测） | Python 模型 `ring_buf.py` 逐项比对；满/空/回绕/跨帧边界；`QUEUECHK` |
| A4 | 写 `sram_arbiter.v`（4 路仲裁，按 §2.3 策略） | 压力模型：读 0.91 MB/s 需求下零饥饿；实测带宽 ≥20 MB/s |
| A5 | 集成：PCM bridge 改用 SRAM 区 B（BRAM 省 4 块） | PCM 逐字节零 diff；`RATECHK`/`AVCHK` 通过 |
| A6 | 集成：码流预取用区 A，SD 调度改为"填满 12 帧即停" | 构造 400 ms 卡忙，播放零中断；`BWCHECK` |

### 2.5 判据（S2-A 完成条件）

- BRAM 增量 **≤15 块**（总 ≤54/64），LUT 增量在 S2 结束时复测
- SRAM 持续读带宽 ≥20 MB/s（`BANDCHK`，由 50 MHz 时钟计数实测）
- 人为注入 400 ms SD 停顿，视频不丢帧、音频不欠载
- 照片/音乐/卡带三路功能与性能**不变**（原有全部回归通过）

## 3. 方案 B：SD 吐字节状态机 1024 → 512 拍

### 3.1 现状依据（实测代码，非猜测）

`src/user_source/hdl_source/media/sd/sd_stream_reader_core.v` 的排空状态机（约 159–193 行）：

```verilog
ST_DRAIN_SET: begin
    state <= ST_DRAIN_GET;          // 1 拍：给地址
end
ST_DRAIN_GET: begin
    if (stream_ready) begin
        ... drain_addr <= drain_addr + 1;
        state <= ST_DRAIN_SET;      // 1 拍：取数据
    end
end
```

**每字节 2 拍** → 512 字节/扇区 = **1024 拍 @50 MHz = 20.48 µs** 的纯开销。

这笔开销在扇区时间里的占比：

| SPI 频率 | 512 B 数据时间 | 开销 20.48 µs | 开销占比 | 有效速率 |
|---|---|---|---|---|
| 6.25 MHz | 655.4 µs | 20.48 | 3.0% | 0.757 MB/s |
| 12.5 MHz | 327.7 µs | 20.48 | **5.9%** | **1.47 MB/s** |
| 25 MHz | 163.8 µs | 20.48 | 11.1% | 2.78 MB/s |

### 3.2 改法

把 `ST_DRAIN_SET` 与 `ST_DRAIN_GET` 合并为**一拍吐一字节**：
BRAM 同步读端口给出的是"上一拍地址"的数据，因此可以让 `drain_addr` 每拍自增，
`stream_valid` 直接来自"本拍有地址在途"的标志，数据则用**上一拍读出的值**（一拍流水）。

要点：
- 保持 ready/valid 语义不变（`!stream_ready` 时**地址不自增、数据保持不变**）
- 扇区末字节的 `sectors_left`/`done` 判定仍按原逻辑
- **不改**厂商命令层（`sd_card_control.v`、`spi_driver.v` 等）
- 加一个参数开关 `DRAIN_1CYC`（默认开），便于 A/B 对比与回归定位

### 3.3 收益

| SPI | 改前有效 | 改后有效（开销 10.24 µs） | 是否过 1.50 MB/s |
|---|---|---|---|
| 12.5 MHz | 1.47 MB/s | **1.512 MB/s** | ✅ **刚好过线** |
| 25 MHz | 2.78 MB/s | **2.94 MB/s** | ✅ 大幅过线 |

**这是本方案最重要的一条**：它让 **12.5 MHz 就满足门槛**，不必赌 25 MHz 的卡兼容性。

### 3.4 实施步骤（S1-B）

| 步 | 内容 | 判据 |
|---|---|---|
| B1 | 增加 `DRAIN_1CYC` 参数，实现单拍吐字节路径（与原路径并存） | 两模式在同一 JPEG/扇区输入下**输出字节流完全一致**（`BYTECHK`） |
| B2 | 单扇区吞吐仿真：统计 512 字节消耗拍数 | `DRAIN_1CYC=1` 时 ≤520 拍；`=0` 时 ≈1030 拍 |
| B3 | 三路功能回归（照片 BMP 加载 / 音乐 WAV / 卡带加载） | 原有全部判据通过（`CHUNKCHK`/`RATECHK`/`BADC0UNT=0`/卡带 `WC=604`） |
| B4 | TD 综合，检查该模块新增逻辑不恶化 sys 域时序 | sys 域裕量 ≥ +1.5 ns（现值 +2.18） |

### 3.5 判据（S1-B 完成条件）

- 12.5 MHz 下测得有效载荷 **≥1.50 MB/s**（用户板上验收，见 §5）
- 三路功能零回归
- `DRAIN_1CYC=0` 仍可回退（保留开关）

## 4. 方案 C：降级顺序调整为「压缩比 → 帧率 → 分辨率」

### 4.1 依据（带宽表，按 640×480 计算）

| 方案 | 帧大小 | 视频码率 | +音频 | SDRAM 写入 | 12.5 MHz 余量（改后 1.512） |
|---|---|---|---|---|---|
| @24, q=4 | 30 KB | 0.72 MB/s | 0.91 | 14.75 MB/s | 66% |
| **@24, q=6** | **25 KB** | **0.60** | **0.79** | 14.75 | **91%** |
| **@20, q=6** | 25 KB | 0.50 | 0.69 | **12.29** | **119%** |
| @15, q=6 | 25 KB | 0.375 | 0.57 | 9.22 | 165% |

### 4.2 门槛（写入设计文档的准入规则）

1. **第一级：提高压缩比**。q 从 4 起，逐级升到 6（画质损失在 MJPEG 下几乎不可见），
   仍超则到 8；每级都要跑 `CORE_CYCLES` 逐帧检查（周期比码率更关键，见 D1 报告 §2）。
2. **第二级：降帧率 24 → 20**。允许直接启用，不需额外批准；20 fps 对 MV 演示无观感损失。
3. **第三级：降帧率 20 → 15**。需要用户书面同意。
4. **第四级：降分辨率**。**需要用户书面同意**，且优先 480×360（保持 4:3 与 16 整除），
   不采用 640×360（非 4:3 变形）。

**明确禁止**：自动、静默地改变分辨率或帧率。任何降级都必须在转换报告里打印清楚，
并在 YXV 头里如实记录实际 fps。

## 5. 实施顺序与门禁

```
现在 ──► S1-B（吐字节优化，2 天）
         ├─ 代码 + 两模式一致性仿真 + 三路回归          ← Codex 交付
         └─ 用户本地：TD 构建 → 烧写 → 实测 12.5MHz 有效速率   ← 硬门禁
              │
              ├─ ≥1.50 MB/s ？ ── 否 ──► 才考虑升 25 MHz，仍不行则启用 q=6/@20 降级
              │
             是
              ▼
         S2-A（SRAM 集成，2–3 天）
         ├─ A1→A4 模块级（Codex 交付，含 Python 模型与判据）
         └─ A5→A6 集成 + 用户板上验收（400ms 卡忙注入）  ← 硬门禁
              │
              ▼
         D2（SDRAM 带地址突发侧口）→ D3…D9 按原设计推进
```

**门禁原则**：S1-B 与 S2-A 各自独立验收；任一不通过就停在那一步调整，
不允许"两件事一起改然后一起调"（本项目历史上叠加改动导致过多次定位困难）。

## 6. 验收判据总表（新增）

| 判据名 | 自动判定关系 | 阶段 |
|---|---|---|
| `DRAINCHK` | 单扇区 512 字节在 `DRAIN_1CYC=1` 下消耗拍数 ≤520，且输出字节流与 `=0` 模式逐字节一致 | S1-B |
| `EFFCHK` | 有效载荷 = 有效字节 / (扇区时间 - 命令开销) ≥1.50 MB/s @12.5 MHz | S1-B（用户实测） |
| `BANDCHK` | SRAM 持续读带宽 = 传输字节/(时钟拍/50e6) ≥20 MB/s | S2-A |
| `JITTERCHK` | 注入 400 ms SD 停顿，视频零丢帧、音频零欠载、缓冲不溢出 | S2-A |
| `BRAMCHK` | TD 报告 BRAM 增量 ≤15 块（总 ≤54/64） | S2-A |
| `REGRESS` | 照片/音乐/卡带三路原有判据全过（`CHUNKCHK`/`RATECHK`/`BADC0UNT=0`/`WC`） | S1-B、S2-A |

## 7. 明确不做的事

- ❌ 不改 `al_ip/`、`src/5640/`、HDMI enc IP、SD 厂商命令层
- ❌ 不改分辨率默认值（640×480 是硬目标）
- ❌ 不在本任务里动 `main` 分支或已冻结固件
- ❌ 不为了省资源而删现有功能（照片轮播/淡入淡出/PSG/遥测都要保留）
- ❌ 不使用 SRAM 做帧缓冲（512 KB < 640×480×2 B = 614 KB，容量不足；SRAM 只做码流/音频缓冲）

## 附录 A：SRAM 引脚冲突比对结果（本次实测）

| 项 | 结果 |
|---|---|
| 主工程约束引脚 | 124 个（其中 tft/camera/gpio/eth 属"约束但电路未连"的空闲项） |
| 主工程实际在用 | 38 个 |

| 与"实际在用"信号的冲突 | **仅 clk 与 uart** —— 同一根线的正常复用，不是资源冲突 |
| 与"空闲约束"引脚的重叠 | **无** |

**结论**：SRAM 的 39 个专用引脚可全部直接使用，只需在 `IO.adc` 追加约束，不影响任何现有功能。

## 附录 B：SRAM 控制器时序摘要（来自 `sram_async_ctrl.v`）

```
写：S_WRITE_SETUP → S_WRITE_PULSE(WE#低) → S_WRITE_HOLD → S_DONE   （4 拍）
读：S_READ_SETUP(CE#/OE#低) → S_READ_WAIT → S_READ_CAPTURE → S_DONE（4 拍）
数据总线：写时由 FPGA 驱动，读时释放（三态），靠 oe_n 控制方向
```

**不要改动这四拍时序**——它对应 10 ns 器件手册的建立/保持要求，是随板工程已验证的取值。

> 词数说明（2026-10-31 校正）：`invaders.yxc` 实为 **604 词**（1844 B = 32 B 头 + 604×3 B，头部 words 字段与 `yxa` 重建一致）。历史文档 `HANDOFF_20261029.md` 记的 606 词是 10-29 07:07 的旧版本，同日 18:13 调游戏手感后变更为 604。遥测 `WC` 对应当前镜像应为 **25C**（604），若读到 25A（606）说明板上是旧卡带。
