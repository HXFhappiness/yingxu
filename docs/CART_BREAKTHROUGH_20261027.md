# 2026-10-27 续：卡带在板上跑起来了

## 突破

板级截图对照（自检 vs 卡带）证明 **CPU 从程序 RAM 取指、执行、提交精灵，全链路已通**。

**根因：取指延迟错位。** TD 推断的 BRAM 是**两拍读**（地址寄存 + 输出寄存），
而 CPU 按一拍设计，于是每条指令都错位一格 —— 所以"程序写对了却跑飞"。
修复：程序地址先打一拍（`raddr_q`）+ CPU 增加 `S_WAIT` 等待状态，把取指延迟显式定为 2 拍。

## 关键排错手段（可复用）

- `test_mode`（板上 SW0 ON）：CPU 从**纯组合 ROM**（case 语句）取指，完全不碰 RAM。
  自检精灵能出现 → 证明 CPU 核 / 暂存 / 提交 / 显示全正常，把问题锁死在存储器上。
- **LED 是低有效**（`led[i] = ~value[i]`），看灯要按"灭=1"读。
- 板级遥测 D 行字段：`SW LS WC BU SP F PC DW I0 RC I1`

## 当前剩余问题

卡带能跑，但渲染不全：

- 玩家精灵出现在**左下角**（x≈0），而 init 里设的是 `px=77`
- 12 个外星人没画（循环 `LDR R0,[ALIVE+X]` 读回 0 → 全部跳过）
- 两者共同指向：**dram（0x00–0xDF 数据 RAM）写入没落地 / 读回为 0**
- dram 往返自检（写 0x5A → 读回 → 显示 LED）读数异常，说明不是完全不通，而是**值被破坏**

## 下一步

1. 用**砖块层当显示器**：把 dram 读回值写进 `0xE0`（砖块位图字节），
   屏幕上的 10×6 砖块直接显示 8 个 bit，比 LED 直观得多，且不需要新硬件
2. 若确认 dram 写坏 → 把 `dram` 改成显式寄存器堆（224×8 = 1792 个触发器，资源充裕）
3. 通了之后：板上验收打砖块 → 拨 SW6 切流浪者 → 录演示
