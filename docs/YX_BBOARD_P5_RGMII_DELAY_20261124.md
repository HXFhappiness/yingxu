# YX_BBOARD_P5_RGMII_DELAY_20261124 — RGMII 输入 hold：三方案对比与 IDELAY 实测标定

承接 `docs/YX_BBOARD_P5_PHY1_20261124.md` §3（RGMII 输入 hold −3237ps / 10 端点）。
本轮把"接受现状 / eth PLL 相移 / IDELAY 延长数据"三个方案用**实测数字**比完，
选定第三个并用 TD 标定到位。

---

## 0. 一句话结论

RGMII 的采样点原本落在 4ns 数据眼的 **66%**（偏晚）。在数据路径插入
`EG_LOGIC_IDELAY #(.INDEL(3))` 后回到 **48.9%**（≈ 正中），
物理余量 **1.16ns → 1.75ns**，**不增加任何 LUT/BRAM/PLL/GCLK**。

**TD 的 hold 违例不会消失，也不该消失**——见 §4，它与物理余量方向相反。

---

## 1. 问题回顾（为什么采样点偏晚）

RGMII 在 PHY 引脚上数据与 RXC **边沿对齐**（数据翻转与时钟沿同时发生）。
进 FPGA 后两条路径的插入延时不同（TD 实测，`eth_rxd[0]`）：

| 路径 | 组成 | 合计 |
|---|---|---|
| 数据 → IDDR.d | PAD 1.075ns | **1.075ns** |
| 时钟 → IDDR.clk | PAD 1.831 + BUFG 0.000 + 网 1.874 | **3.705ns** |

时钟比数据晚 **2.63ns**，而一个 bit 只有 4ns（125MHz DDR）：

```
采样点 = 2.63 / 4 = 65.8%     （理想 50%）
到下一位翻转的余量 = 4 − 2.63 = 1.37ns
扣 IDDR hold 0.207ns            → 实际余量 1.16ns
```

这个 2.63ns 不是设计出来的——它是**布线副产物**，把"平面对齐"意外变成了"中心对齐"。

## 2. 三个方案的实际差异

| | 改什么 | 采样点可控性 | 新增资源 | 参数怎么定 |
|---|---|---|---|---|
| **A 接受现状** | 无 | 不可控 | 0 | — |
| **B eth PLL 受控相移** | 时钟树 | 可控（相移步进较粗） | **新 PLL IP（EG4 共 4 个，已用 2）** + **新增时钟域**（SDC 要加 clock group） | STA 可读 |
| **C IDELAY 延长数据** | 数据路径 5 根线 | 可控（实测可分辨 0.07~0.1ns） | **0**（IOB 内资源，LUT/BRAM/PLL/GCLK 全不变） | STA 可读 |

### B 的一个反直觉点

PLL 自己会**增加**时钟插入延时（本设计 HDMI PLL 实测 1.214ns）。所以"插个 PLL"
不会自动变好：时钟路径 3.705 → ~4.9ns，相对差变 3.83ns ≈ 眼的 96%，**更差**。
要回到 50% 得给约 **−1.83ns 的相移（≈ −82°）**，即"先抵消 PLL 自身的延时，再谈对齐"。
相移方向和绝对量只能上板标定。

### 为什么选 C

1. 不引入新时钟域、不占 PLL、不改 `set_clock_groups`——改动面只有 5 根线；
2. EG4 的 `EG_LOGIC_IDELAY` 落在 IOB 内，**资源零增量**（实测 LUT/BRAM/PLL/GCLK 全不变）；
3. 效果直接体现在 TD 报告的 `Data Path Delay` 上，可以工具内闭环标定；
4. 全链路仿真判据完全不受影响（见 §5）。

## 3. 实测标定（EG4 真实模型，不是仿真库标称值）

`EG_LOGIC_IDELAY` 的仿真库标称是"基础 0.52ns，每档 0.12ns"
（`sim_release/eg4/eg_logic_io.v:25`）。**实测与标称不符**，不能按标称推算档位：

| INDEL | Data Path Delay | PAD | 附加延时 | 数据路径合计 | 时钟 | 相对差 | 采样点 | 物理余量 |
|---|---|---|---|---|---|---|---|---|
| 无 IDELAY | 0.675ns | 1.075 | — | 1.075ns | 3.705 | 2.630ns | 65.8% | 1.16ns |
| 1 | 1.147ns | 1.547 | +0.472ns | 1.547ns | 3.705 | 2.158ns | 54.0% | 1.64ns |
| **3（采用）** | **1.348ns** | **1.748** | **+0.673ns** | **1.748ns** | **3.705** | **1.957ns** | **48.9%** | **1.75ns** |
| 32 | 3.300ns | 3.700 | +2.625ns | 3.700ns | 3.185* | −0.5~0.005ns | ≈0% | **负（坏）** |

\* INDEL=32 那次 build 的时钟插入延时变成了 3.185ns（不是 3.705），说明
**插入延时在两次 P&R 之间会漂移**。无论按哪个值算，TAP=32 的采样点都落在数据
翻转点上（相对差 ≈ 0 或负），物理上必然失败。

→ 目标"附加 0.63ns"最接近的是 **INDEL=3（+0.673ns）**，采样点 48.9%，余量 1.75ns。
（48.9% 与 50% 差 0.043ns，可忽略。）

---

## 4. ★★ 最重要的发现：TD 的 hold slack 与物理余量**方向相反**

同一份设计，只改 IDELAY 档位，三个观测点：

| INDEL | TD hold slack | 采样点 | 物理余量 |
|---|---|---|---|
| 1 | −2.765ns | 54.0% | 1.64ns |
| **3** | **−2.564ns**（比 TAP=1 更"差"） | **48.9%** | **1.75ns ← 最优** |
| 32 | **−0.092ns**（几乎"通过"） | ≈0% | **负 ← 最差** |

**slack 越"好看"，设计越坏。**

原因在判据本身：

```
hold_slack = input_delay_min + PAD − (clk_latency + hold)
           = -0.400        + PAD − (3.705     + 0.207)
```

它要求**数据在捕获时钟之后到达**（即 `data_path ≥ 3.912ns`）。而本设计恰恰
靠"时钟晚于数据"实现中心对齐——数据越早到（相对差越大），物理余量越好，
但这一项 slack 就越负。

所以：

- 这条违例**永远留着**，不管 IDELAY 怎么调；
- **调参只看采样点位置（相对差 / 4ns），绝不看 slack**；
- 若哪天有人为了让报告变绿去加大 INDEL，会把设计调向崩溃（TAP=32 就是活教材）。

---

## 5. ★ TD 的坑：`INDEL` 必须用**字面量**，不能用模块 parameter 传递

实测（EG4，TD Release_2026.2）：把值写成模块体内 parameter 再传给原语——

```verilog
parameter [4:0] RX_IDEL_TAP = 5'd32;                 // ← 模块体内
EG_LOGIC_IDELAY #(.INDEL(RX_IDEL_TAP)) u_idel (...); // ← 传给原语
```

`INDEL` 取 2 / 3 / 32，TD **全部按默认档（INDEL=1）实现**，
三次报告里 `Data Path Delay` 恒为 `1.147ns`。改成字面量：

```verilog
EG_LOGIC_IDELAY #(.INDEL(3)) u_idel (...);   // ← 立即响应，1.348ns
```

原因未查明（疑似 TD 对"模块 parameter → 原语 parameter"的常量传播不完整，
或对 generate 内参数化实例的处理有缺陷）。

**结论：`INDEL` 必须写字面量。** 不要为"优雅"改回参数化——那会让调参**静默失效**
（编译通过、报告不变、你以为改生效了）。

## 6. 仿真侧处理：直通 shim

厂商原语在 iverilog 里没有模型，新增 `tb/bshims/EG_LOGIC_IDELAY.v`：

```verilog
module EG_LOGIC_IDELAY #(parameter INDEL = 1) (input wire i, output wire o);
    assign o = i;          // 直通，无附加延时
endmodule
```

**为什么直通而不是加 0.67ns：**

1. IDELAY 只改变数据相对时钟的**到达时刻**，不改变任何逻辑值 → 直通在功能上精确等价，
   **不放宽任何判据**（字节对拍 / 金标判据全部不变，实测 `eth_rx`
   `ok=290 drop=1 byte_cnt=295941 cmp_errs=0` 与历史完全一致）；
2. 仿真里根本没有真实插入延时（时钟 3.705ns、数据 1.075ns）。若在仿真里也加 0.67ns
   数据延时，反而会**伪造**"数据比时钟晚"的关系——物理上恰好相反。**加延时才是失真。**

该 shim 需加入三个以太网入口的源单（`eth_rx` / `bboard_sys_eth` / `bboard_key`；
`bboard_sys` 不含 `rgmii_to_gmii.v` 故不需要）。

## 8. 遗留

1. **最终余量仍需上板确认**（三个方案共同限制）。三条工具管不到的误差源：
   STA 延时模型误差（通常 10~20%）、RTL8211F 的 RXD↔RXC 输出偏斜规格
   （**手上没有该 datasheet**，目前沿用厂商模板的 +0.5/−0.4）、PCB 走线等长误差。
   标称余量 1.75ns，按 ±0.5ns 偏斜估最坏 1.25ns。
2. **`INDEL=3` 是按本次 build 标定的**。插入延时会在 P&R 之间漂移
   （实测见过 3.705 → 3.185）。**每次重新综合/布局后应复核**：
   读 `eth_rxd[0]` hold 路径的 `Clock Skew` 与 `PAD`，目标 `Clock Skew − PAD ≈ 2.0ns`。
3. **IDELAY 无法旁路**：最小档 INDEL=1 就有 0.472ns。若某次 build 相对差已 ≤ 2.0ns，
   加延时反而过冲，届时应复核是否保留该段。
4. 顺带印证了 `YX_BBOARD_P5_PHY1_20261124.md` §3 的判断：RGMII hold 违例是
   判据/拓扑模型冲突，**不是**待修的 RTL 缺陷。现已有量化证据（§4）。
