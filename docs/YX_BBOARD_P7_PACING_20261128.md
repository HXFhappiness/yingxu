日期：2026-11-28 / 版本：0.17.0 / 基线：`645fb25`（P6 全部闭合）
状态：**FIFO 扩容完成且无回退；提速率的边界已实测——结论修正见 §3**

## 1. FIFO 扩容：8KB → 16KB（AW 13→14）

### 1.1 预算推导（为什么是 16KB 不是 64KB）

| 方案 | 位宽 | 占用 | 可行性 |
|---|---|---|---|
| 8KB（现状 AW=13） | 8192×8 = 65,536 bit | 8 × bram9k（实测 `u_bfifo` 8 块） | bram9k 46/48，只剩 2 |
| **16KB（AW=14）** | 16384×8 = 131,072 bit | **4 × bram32k** | ✅ bram32k 10/16，余 6 |
| 24KB（AW=15） | 196,608 bit | 6 × bram32k | ⚠️ 恰好用光全部空闲 |
| 64KB（AW=16） | 524,288 bit | 16 × bram32k | ❌ 只有 6 块空闲 |

**存储必须显式例化 `EG_LOGIC_BRAM` 并指定 `IMPLEMENT="32K"`**：16K 深度若走
推断路径，bram9k 池（余 2 块，需 ~16 块）装不下，TD 会按资源上限把存储踢成
分布式 RAM（P5 实测 ~15.7K LUT 的重演）；推断路径永远拿不到 32Kb 池
（`yx_vp_band.v` 的 book/ln32 同款结论）。

### 1.2 实施
- `yx_b_afifo` 增加 `BRAM` 参数：0 = reg 数组推断（描述符 FIFO 等小 FIFO 沿用），
  1 = 显式 `EG_LOGIC_BRAM #(.IMPLEMENT("32K"))`（真双口：A 写 @125M / B 读 @100M）。
- `u_bfifo` 传 `BRAM(1)`；`u_dfifo`（8 深 × 16bit）保持推断——8 深存储例化 BRAM 原语不划算。
- **读出时序逐拍等价**（这是改动安全性的根据）：数组 `dout_r <= mem[mem_ra]` 与
  BRAM 同步读（地址当拍沿锁存、下一拍 dob 出现同地址的值）语义相同，故
  `rd_data` 直接取 `dob`，`dvalid` 指针逻辑一行未改。
- 深度相关阈值核查：`fifo_room = DEPTH − occ`、`start_ok`（room ≥ len+16）、
  `data_ovf = pv & byte_full`、`wr_full`（格雷判定）全部由 `FIFO_AW` 派生，无写死常数。
- 例化点：`yx_b_eth_rx.v` 默认参数 13→14、`yingxu_vq_board_top.v`（TD 构建）13→14、
  `tb_yxvp_bboard.v` 的 `u_ethrx` 13→14。
- **随带发现并修复：描述符 FIFO 也必须同步扩容（DESC_AW 3→4）**。字节 FIFO 扩到
  16KB 后，自适应发送方（sys_eth 的 TB 等 room 再发包）可以连发 ~15 个包才把
  字节 FIFO 填满，但描述符 FIFO 只有 8 深 → 第 9 个包 `start_ok=!desc_full` 被
  整包拒收。实测 sys_eth 首跑 `ok=160/292 drop=132`（eth_stress 同构 160/132），
  DESC_AW=4（16 深）后恢复 `ok=292/292 drop=0`。**8KB 时代没暴露，是因为
  字节 FIFO 先满（8,192/1,066≈7.7 包 < 8 描述符）恰好把发送方节流住了。**
  预算：16,384B 最多容纳 15 个整包 + 1 个在途 = 16 个描述符，DESC_AW=4 恰好够。

### 1.3 扩容后无回退验证
| 项 | P6（8KB） | P7-a（16KB） | 判定 |
|---|---|---|---|
| SWNS | +0.432 ns | **+0.199 ns** | 仍为正 ✓（−233ps 来自 BRAM 原语布线） |
| bram32k | 10/16 | **14/16**（+4，恰如预算） | ✓ |
| u_bfifo 占用 | 8 块（bram9k） | **4 块**（bram32k） | ✓ 落位 |
| bram9k | 46/48 | 38（释放 8） | ✓ |
| #lut | ~4,235 | 4,320 | ✓ 无爆炸（未退化分布式 RAM） |
| `eth_rx`（字节精确） | PASS | **PASS**（`cmp_errs=0`、`out_bytes=295941` 精确） | ✓ |
| bit 文件 | 无 | 无（双预检） | ✓ 红线守住 |

`bboard_sys_eth` / `eth_stress` / `bboard_key` / `bboard_sys` / `mdio` / `phy_init`
在 16KB 下的复跑结果见 §5。

## 2. 提速率：第一档（KEY 28ms / 4.11 MB/s）→ **丢包，边界值记录**

FIFO 16KB 后，按原计划把 KEY 从 96ms（1.2 MB/s）提到 28ms（**4.11 MB/s**）：
丢包阈值推算 ≈ 14,896（room 判定）+ 在途 2,800 ≈ 17,700 B，2.5ms 死窗允许
KEY ≤6.5 MB/s，4.11 应有 1.5× 余量。

**实测（out/sim/p7_e2e.log，WD=14M 提前停）**：

| t (clk100) | B 消费 | room | 缺口 | drop |
|---|---|---|---|---|
| 5.00M | 156,182 | 10,290 | — | 0 |
| 5.25M | **163,639（冻结）** | 8,360 | 8,577 | 0 |
| 5.50M | 163,639 | 5,411 | 18,535 | **5** |
| 6.00M | 163,639 | 5,398 | 38,451 | 18 |
| 6.75M | 186,383（爆发恢复） | 16,354 | 45,581 | **30** |

**关键发现：死窗不是常数，且随速率增长。**
- P6（KEY 1.2 MB/s）：死窗 ≤5.5ms（8KB 下零丢包反推）；
- P7-a 本轮（KEY 4.11 MB/s）：**消费冻结 5.1M → 6.6M ≈ 15ms**（1.5M 拍），
  期间 B 的 FIFO 里躺着 ~11KB 数据却一个字节不消费（`stream_ready=0`，
  `ixwr` 写带宽被渲染/扫描占用 → skid 满）。
- 恢复后单窗喝 22,744 B（≈线速）——B 的消费形态是**线速爆发 + 长停顿**。
- 机理：死窗 = ixdec 吃完上一帧后的**解码收尾 + 窗口提交 + ixwr 排空**，
  时长取决于流水线积压深度——A 推得越快、积压越深、死窗越长（超线性）。
  这正是 P5 文档"瓶颈是索引写 FIFO 的延迟"的现象，在更快节奏下被放大。

**边界值：KEY 4.11 MB/s（等效均匀口径 ≈ BYTE_DIV 26）→ 丢包。**

## 4. stall2 语义与基线（修正认知）

`stall2` = `pend_cnt==2`（band 渲染完 2 帧的带、scanout 还没 ack）= **渲染器被
显示侧堵住**，即"扫描/显示 60fps 固定节拍成为限速方"。

| 场景 | stall2 | 含义 |
|---|---|---|
| `bboard_key`（文件馈送，无网络） | **36%**（2,768,436/7,576,651） | 解码+渲染跑在显示前面，显示节拍限速 |
| `bboard_sys_eth`（TB 自适应：等 room 再发包） | 17% | 网络节奏介于两者之间 |
| `p6_e2e`（P6 慢速开环 1.07 MB/s） | 0.13% | A 是限速方，渲染永远等得到数据 |

**结论**：`stall2 ≥30%` 等价于"A 不再限速、B 的解码+渲染跑出了文件馈送速度"。

## 6. 结论与后续

**本轮修正了 P6 文档 §8 的一个隐含假设**：死窗不是固定的 2.5ms——它是 B 的
帧边界串行化延迟（解码收尾 + 窗口提交 + ixwr 排空），**随 A 的节奏超线性增长**
（1.07 MB/s → ≤5.5ms；4.11 MB/s → ~15ms）。因此"FIFO 深度 × 固定死窗"的
预算方法不成立；FIFO 深度必须按**目标速率下的实测死窗**定。

**量化结论**（16KB FIFO、丢包阈值 ~17.7k deficit、实测死窗 15ms@4.11 档）：
- KEY ≤2.0 MB/s（57.6ms 窗）→ **零丢包实测通过**（本轮交付档）
- KEY 4.11 MB/s → 丢 30 包（实测边界）
- 60fps（KEY 8.26 MB/s）需要吸收 ~8.26 × 15ms ≈ 124 KB → **16KB 远不够**；
  且死窗随节奏增长（1.07 MB/s 档 ≤5.5ms → 4.11 档 ~15ms），更大 FIFO 的收益
  会被更长的死窗吃掉——24KB（用光全部空闲 bram32k）按 15ms 死窗也只支撑
  ~1.5 MB/s。**结论：开环 + 现有 BRAM 预算无法实时，加 FIFO 此路不通。**

**三条出路**（按推荐序，均超出本轮范围）：
1. **A→B 反压/信用通道**：B 的 `fifo_room` 信号现成（`start_ok` 判定用的就是它）。
   半自适应后 16KB 即可支撑 KEY 4.11+ MB/s（本轮第一档的缺口全部来自开环盲发）。
2. **B 侧 RTL：消掉帧边界串行化**（ixdec 解码收尾与下一帧 ingest 重叠、
   ixwr 与 band 的 SDRAM 仲裁加权）——死窗从 15ms 压到 ≤2.5ms 时，
   16KB 可支撑 5.4 MB/s ≥ 源码率。
3. ~~更大 FIFO~~：见上，24KB 不够、64KB 装不下，**此路不通**（本轮实测修正）。
