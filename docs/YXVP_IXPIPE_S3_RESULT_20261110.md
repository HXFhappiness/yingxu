# YX-VP 索引管线（方案 A）验收报告 — 2026-11-10

## 1. 结论

**方案 A 索引管线（ixdec → ixbuf → band → SDRAM 模型 → 逐带比对）全链路仿真验收通过。**

| 几何 | 流 | 帧数 | 比对带数 | 失败带 | 结果 |
|---|---|---|---|---|---|
| 256×144 VQ-1024 | vp_s1024.yxv2（4×KEY + 36×DELTA 混合流） | 40 | 1440 | **0** | **ALL PASS**（1,838,634 clk 自然退出） |
| 1280×720 VQ-1024 | vp_720_5f.yxv2（2×KEY + 3×DELTA） | 5 | 900 | **0** | **ALL PASS**（5,942,376 clk） |
| 1920×1080 VQ-256 | vp_1080_5f.yxv2（AW=19 自适应） | 5 | 1350 | **0** | **ALL PASS**（13,402,156 clk） |

验收方式：每带 `band_done` 时，TB 用 Python 参考解码器（`vq_decode_delta.py --dump`）导出的
`ref.bin` 对应 4 行做**逐位对拍**；行缓冲 `ln` 数组直接层级引用读取。参考与 RTL 共用同一
YXV2 位流与码本 hex，任何一处索引/查表/地址错误都会以像素失配形式暴露。

## 2. 架构（重申）

DELTA 帧与"旋转 RGB565 槽"互斥（槽里是 N-3 帧的像素，DELTA 需要 N-1 帧的索引），
因此采用**索引帧缓冲**：

```
字节流(YXV2) → yx_vp_ixdec ──(blk,idx)补丁字──> yx_vp_ixbuf ──写口──> SDRAM
                  │ 16深skid        │ 双索引缓冲                    │ 读口B
                  │                 │ 拷贝-补丁-翻转                ▼
                  │                 │ busy×2 所有权            yx_vp_band
                  │                 │ DELTA宣布→COPY           索引→码本BRAM→行缓冲
                  │                 ▼                              │ band_done/ack
                  └──────────> swap_done/commit_no ────────────────┘
```

- **ixbuf 相态机**：READY（收补丁，写 target）→ DRAIN（排空补丁 FIFO）→ WAITFREE
  （等渲染器让出 target）→ SWAP（act 翻转、commit++、swap_done 脉冲）→（挂起 DELTA 宣布）→
  COPY（串行拷贝 active→target，accept=0）→ READY。
- **缓冲所有权**：帧 k 恒用缓冲 k[0]（严格交替）；`busy[i]` 表示渲染器正在读缓冲 i，
  渲染完成（rendered_no 变更沿）释放。补丁接收 `ix_rdy = READY && FIFO有位 && !busy[target]`，
  拷贝读请求同样等 `!busy[target]` —— **解码器最多领先渲染器 2 帧**。
- **band**：整帧渲染完回 IDLE 等下一帧（渲染中到来的 swap_done 锁存为挂起帧，不跳帧）；
  行缓冲 2 带 ping-pong，扫描端消费回 ack 才推进。
- SDRAM 行为模型：写口 1/3 拍节流 + 每 8192 拍刷新停摆 64 拍；读口×2（拷贝/取带）各 1 拍/字，
  读请求电平保持过刷新窗。

带宽核算（720p@24，方案 A）：索引扫描 27.6 + 拷贝 2.8 + 补丁 1.2 + 音频 ≈ **31 MB/s**
（RGB565 三缓冲方案需 ~190 MB/s），6 倍节省，75 MHz SDRAM 亦有裕量。

## 3. 本轮调试修复台账（12 项，全部有仿真证据）

| # | 模块 | 缺陷 | 证据 |
|---|---|---|---|
| 1 | ixbuf | 补丁 FIFO `pf_rp` 出队不推进 → 永远吐 `pf_mem[0]` | 写轨迹 addr=0/8/32/56 各写 8 次；SDRAM 131072 字中 130783 个 X |
| 2 | ixbuf | DELTA 宣布走 SWAP 不走 COPY，`pend_v` 从未置位 | 代码审计：`pend_v <= 1'b1` 全文无一处 |
| 3 | band | 整帧渲染完不回 IDLE → 永远重渲第 0 帧 → `busy[1]` 永不释放 → 解码器饿死 | POLL：rend=0 恒定、ixphase=3 卡死 |
| 4 | band | `wire q_row = wp[3:2]` 隐式 1 位宽（iverilog 默认 1 bit）→ 行缓冲写地址塌缩 | LNW 探针：wa=0,1,0,1,256,257…（每块只落 2 像素） |
| 5 | ixdec | `bcnt` 发射后不复位 → 每块只吞 1 字节、索引错位 | 写数据 0306/0206 交替；参考帧 0 应全 0306 |
| 6 | band | BOOK 等待拍未预增 `book_ra` → wp≥1 查表滞后一码本项 | LNW2：wp=1 d=f79e（应为 f79d） |
| 7 | ixdec | skid FIFO `q_cnt` 同时扣 pop 与 load → 下溢回绕 31 → 反复吐陈旧字 | push=957621 对 emit=5008；写口反复敲同一地址 |
| 8 | ixdec | `S_DIDX` 缺 `q_room` 门控（S_KEY 有）→ skid 满时生产者被按住、FSM 幻影吞字节 | FDONE7 sent=11711 少 3 字节（奇数），后续帧头全错 |
| 9 | ixdec | **`frame_kind` 输出从未驱动（恒 Z）** → ixbuf 判帧型恒假 → 拷贝引擎从未启动 | FSTART 探针 kind=z；CPSTART 零次；FETCH f1b0 data=xxxx |
| 10 | ixbuf | READY 相态消费挂起 DELTA 宣布 → act 未翻转就起拷贝，src/dst 全错 | f2 拷贝把 B0 再抄一遍覆盖 f1 补丁 |
| 11 | ixbuf | 补丁接收不看 busy → KEY 帧补丁覆写渲染器正在读的缓冲 | 隔帧全错（f1/f4/f6… err=1024）；f3 KEY 补丁污染渲染中的 B1 |
| 12 | TB | fd 计数在主循环与专用块重复累加；退出条件按解码 fd 而非渲染完成 | 21 个 fd 凑满 40 提前退出 |

其中 #9 最具隐蔽性：S2 KEY-only 测试里 Z 恰好等价于"非 DELTA"，测试通过反而掩盖了缺陷。
**教训：输出端口必须逐个确认驱动；对 Z 的"碰巧正确"要保持警惕。**

## 5. 节奏与余量

- **256×144@50MHz**：40 帧 1.84M clk（含 1/3 写节流与刷新停摆压力条件）；渲染器是瓶颈
  （36 带 × ~1250 clk/帧），解码器领先约 2 帧收尾（FDONE40 时渲染器在帧 38）。
- **720p@50MHz**：5 帧 5.94M clk → **23.8ms/帧**。渲染 6600 clk/带（320 块 × ~20 clk）。
  换算真实余量：**720p@24fps（41.7ms/帧）裕量 1.75×**；720p@60 需视频域 ≥100MHz
  （11.9ms/帧，可行）。每帧 DELTA 拷贝 57600 字 × ~3 clk ≈ 0.35ms，被 busy 所有权自然节流。
- **1080p@50MHz**：5 帧 13.4M clk → **53.6ms/帧**。渲染 9900 clk/带（480 块 × ~20 clk）。
  **1080p@24fps（41.7ms/帧）需视频域 ≥75MHz**（35.8ms/帧，裕量 1.17×）；
  100MHz 时 26.8ms/帧，裕量 1.55×。与既定"1080p@24 走 75MHz 视频域"的档位规划一致。
- 字节核算同样逐帧精确（720p FDONE1 sent=115205 = 20+32768+5+57600×2 ✓；
  1080p FDONE1 sent=129605 = 20+8192+5+129600×2 ✓）。
- 真实系统带宽核算（720p@24，方案 A）：索引扫描 27.6 + 拷贝 2.8 + 补丁 1.2 + 音频 ≈ **31 MB/s**
  （RGB565 三缓冲方案需 ~190 MB/s），6 倍节省，75 MHz SDRAM 亦有裕量。
