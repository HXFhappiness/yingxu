# YX-VP-VQ v1 — 自研视频硬解协处理器架构设计

> 状态：设计稿（本轮不接入顶层、不参与烧录验证）
> 定位：B 板（GS 图形坞）上的专用视频硬解流水线，映序"板级协处理器家族"的第一个成员。
> 参照实现：`tools/vq_encode_stream.py` / `tools/vq_decode.py` / `tools/vq_view.py`（YXVQ 格式与 RGB565 码本语义）。

---

## 1. 为什么要自研，为什么第一版选 VQ

映序的"硬解"不打算把视频指令塞进 YX-8 的译码器，也不在本阶段挑战 H.264/HEVC/AV1
（熵解码 + 参考帧 + 运动补偿 + 码率控制会把项目拖进另一个数量级）。
真正可落地、可验收的专用格式是 **VQ（向量量化，4×4 块）**——90 年代 CD 主机
Cinepak 的同族思路，解码本质是**一次查表**：

```text
压缩流 = 每块 1 个索引（1024 项码本 → 16 bit/块 = 1 bpp）
解码   = 码本[index] → 16 个 RGB565 像素 → 写帧缓冲
```

已实测（映序.mp4 样片）：

| 方案 | 分辨率 | 码率 | 解码耗时/帧 | PSNR(Y) |
|---|---|---|---|---|
| MJPEG q6 | 852×480 | 1.24 MB/s | 25 ms @100 MHz（640×480） | 31.11 dB（放大后比 720p 基准） |
| VQ-1024 | 1280×720 | **2.76 MB/s** | **0.6 ms @100 MHz** | 28.23 dB |
| VQ-256 | 1280×720 | 1.38 MB/s | 0.6 ms | 26.56 dB |

VQ-720p 的解码是 MJPEG 的约 **1/180**，且不占用任何 DSP；它把视频从
"100 MHz 域的最大时序违例源"变成一条平凡的数据通路。

## 2. 数据通路（双板形态）

```text
A 板（EE）                                B 板（GS）
┌─────────────────────────┐            ┌──────────────────────────────────┐
│ SD 卡 → 预读取缓冲        │  Ethernet  │ RX FIFO → YX-VP-VQ               │
│ FAT/YXVQ 流解析           │ ────────→ │   ├ 索引 FIFO（跨时钟域）          │
│ 2.76 MB/s 分帧打包        │            │   ├ 码本 BRAM（32 KB，8×BRAM32K） │
│                           │            │   ├ 4×4 展开 → RGB565             │
│                           │            │   └ SDRAM 帧缓冲写口              │
│                           │            │        ↓                          │
│                           │            │   三缓冲 → GS 合成 → HDMI 720p    │
└─────────────────────────┘            └──────────────────────────────────┘
```

单板形态（无 B 板）下 YX-VP-VQ 不启用，视频条目按 `CAP_EXT` 语义降级隐藏。

## 3. 资源预算（EG4S20，B 板）

| 资源 | 用量 | 说明 |
|---|---|---|
| LUT | ~300–500 | 索引对齐 + 展开寄存器 + SDRAM 写对齐；无乘法 |
| DSP | **0** | 无 IDCT、无乘加 |
| BRAM32K | 8 | VQ-1024 码本 = 1024×16×16 bit = 32 KB（该组 BRAM 当前完全空闲） |
| BRAM9K | 2–4 | 索引 FIFO + 帧边界缓冲 |
| SDRAM 带宽 | 写入 2.76 MB/s（远低于扫描输出的 ~110 MB/s） | 三缓冲 3×1.84 MB |

对比被替换的 MJPEG 解码器：约 4,500–5,000 LUT + 21 DSP，全部释放。

## 4. 控制接口（GS 命令序列器视角）

B 板的 GS Command Sequencer 暴露给 A 板的命令（经扩展总线 0xFF 通道承载）：

| 寄存器 | 方向 | 语义 |
|---|---|---|
| `VP_CTRL` | W | bit0 START，bit1 STOP，bit2 帧缓冲翻转（手动模式） |
| `VP_CODEBOOK` | W | 码本装载窗口：首字 = 条目数（256/1024），随后 32 B/条目 |
| `VP_STREAM` | W | 压缩流数据口（A 板按帧打包写入，B 板 RX FIFO 缓存） |
| `VP_FRAME_BASE` | W | 当前帧的 SDRAM 基地址（三缓冲轮转由 GS 管理） |
| `VP_STATUS` | R | bit0 运行中，bit1 帧完成，bit2 流欠载，bit3 索引越界，bit7 CRC 错 |
| `VP_FRAME_CNT` | R | 已完成帧计数（诊断/演示用） |

命令语义要点：

- **帧边界**：A 板在每帧头部写 4 字节帧长 + 帧号；B 板据此切帧、置 bit1。
- **欠载策略**：FIFO 空时保持上一帧显示（不黑屏），置 bit2 供 A 板调速。
- **索引越界**：索引 ≥ 码本条数时该块写 0（品红诊断色），置 bit3——不中断播放。
- **码本装载**：只在帧间允许；装载中 START 无效。

## 5. 三缓冲与帧提交

720p RGB565 一帧 1.84 MB；8 MB SDRAM 放 3 帧缓冲（5.53 MB）+ RX FIFO 队列区。
播放节奏 24 fps：VQ 解码 0.6 ms ≪ 41.7 ms 帧周期，解码永远追得上显示，
唯一的同步点是"帧完成 → 下一消隐期翻页"。GS 合成器读的缓冲永不与解码写的冲突。

## 6. 与 SD 卡和链路带宽的关系

720p VQ-1024 @24 fps 需要 2.76 MB/s。当前 SD 实测 1.3 MB/s（12.5 MHz SPI），
**不够**；已规划的升级路径：

1. 三相位时钟（400 kHz 初始化 / 6.25 MHz 命令 / 25 MHz 数据）；
2. CMD18 多扇区连读 + CRC16 硬件校验 → 目标 2.4–2.8 MB/s。

Ethernet 链路（千兆 RGMII）对本流量余量极大；百兆也可承载。

## 7. 为什么不做 H.264 / HEVC / AV1（本阶段）

| 维度 | VQ | H.264 baseline |
|---|---|---|
| 熵解码 | 无（定长索引） | CAVAC/CABAC，状态机深 |
| 帧间依赖 | 无（每帧独立） | 参考帧管理 + 运动补偿 |
| DSP | 0 | 数十个乘法器 |
| DRAM | 单帧缓冲 | 多参考帧 |
| 工程量 | 数百行 Verilog | 人年级 |

JPEG 硬解（YX-VP-JPEG）作为二代型号：熵解码可做（定点 Huffman 表），
2D IDCT 需要流水线乘法阵列，在 19,600 LUT 预算里可承载但不便宜——
先让 VQ 在板上跑通，建立"专用格式 + 硬解协处理器"的家族叙事。

## 8. 分阶段验收

| 阶段 | 内容 | 判据 |
|---|---|---|
| S0 | 软件参考链路 | `vq_decode.py` 已完成；720p-1024 全片已编码（2.76 MB/s） |
| S1 | YX-VP-VQ RTL + 单帧仿真 | 与 `vq_decode.py` 输出逐位一致（iverilog） |
| S2 | B 板 SDRAM 直写 | 单板烧录，VQ 文件经 UART/预置写入，HDMI 显示单帧 |
| S3 | Ethernet 流 | A 板发流 → B 板解码显示，帧计数递增 |

S1 之前不改任何板上位流；S2/S3/S4 全部需要烧录，另行征求同意后进行。
