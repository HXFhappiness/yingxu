# 映序精灵引擎技术文档（yingxu_sprite_engine）

> 版本基准：R2（`release\OPT1\V0.4C-OPT1.bit`，2026-10-25 上板验证通过）
> 整理时间：2026-10-25
> 源文件：`src\user_source\hdl_source\yingxu_sprite_engine.v`（约 230 行）


---

## 一、概述

精灵引擎是"映序 = 可重构图形平台"主张的承载者：**同一套逐像素合成通路，为照片浏览、
打砖块、太空侵略者三种完全不同的画面提供服务**。游戏逻辑对画面的全部表达，就是往
一张 16 槽的精灵表里写记录；引擎负责把表"变成像素"。

架构上一句话概括：**以 BRAM 为界的两段式合成器**。

```
                 所有随画面变化的复杂判断（16 槽命中、优先级、砖块、瓦片）
                              ↓ 全部关在渲染侧，喂 BRAM 写口
        ┌──────────────┬──────────────────┐
 渲染侧 │ 逐像素判定     │ → 双行缓冲（RGB565）│
        └──────────────┴────────┬─────────┘
                                 ↓ 每行一条，隔行交替
 显示侧 │ BRAM 读（寄存一拍）→ 565→888 展开 → 单级 mux vs 背景 │ → rgb_out
        └──────────────────────────────────────┘
```

这样切分的理由（v1 的教训）：v1 曾把 16 槽命中+优先级全部组合逻辑直通视频输出，
结果拉长了像素路径，干扰 SDRAM 回放流（竖条纹、一次编译直接无视频）。v2 起，
**显示侧只剩一次 BRAM 查表和一级 mux**，复杂度全部转移到提前一行的渲染侧。

## 二、接口规格

```verilog
yingxu_sprite_engine #(
    .NSLOT(16), .H_ACTIVE(1280), .H_TOTAL(1650),
    .V_ACTIVE(720),  .V_TOTAL(750),
    .BRICK_COLS(10), .BRICK_ROWS(6),
    .BRICK_W(128),   .BRICK_H(32), .BRICK_X0(0), .BRICK_Y0(60)
)
```

| 方向 | 信号 | 宽度 | 说明 |
|---|---|---|---|
| in | clk / rst | 1 | 像素时钟 73.33 MHz / 像素域复位 |
| in | pixel_x / pixel_y / pixel_active | 11/10/1 | 光栅坐标（video_source_test 提供） |
| in | bg_rgb | 24 | 背景（照片回放 / 游戏纯黑 / 故障色），由顶层 mux 出 |
| in | we / slot / en / spr_x / spr_y / spr_w / spr_h / spr_color | — | **精灵表写口**：每时钟最多写一槽 |
| in | brick_mask | 60 | 打砖块砖块存活位图（行优先） |
| in | tile_rgb | 24 | 滚动瓦片层当前像素颜色，0 = 透明 |
| out | rgb_out | 24 | 合成后像素 |

外部实例化只覆盖 NSLOT（`design_top_wrapper`），其余参数用默认值。

## 三、精灵表

```verilog
reg [66:0] spr_tab [0:15];    // 16 槽 × 67 位，综合为分布式 RAM（LUTRAM）
```

位段布局（P2c 后）：

| 位段 | 字段 | 说明 |
|---|---|---|
| [66] | en | 槽使能，0 = 该槽不画 |
| [65:55] | x[10:0] | 左上角 X |
| [54:44] | **xpw[10:0]** | 右边界 **x+w，写表时预计算** |
| [43:34] | y[9:0] | 左上角 Y |
| [33:24] | **yph[9:0]** | 下边界 **y+h，写表时预计算** |
| [23:0] | color[23:0] | RGB888 |

写侧一次算好 `wr_xpw = spr_x + spr_w`、`wr_yph = spr_y + spr_h`——写表每帧仅 16 次，
而命中判断每帧要做上百万次，加法器没有理由留在热路径上。边界宽度与原字段一致，
溢出回绕行为与旧版完全相同（游戏数据最大 x+w ≈ 1400 < 2048，实际不会触发）。

## 四、双行缓冲与行流水

```verilog
reg [15:0] ovl [0:4095];      // 2 × 2048 × 16bit，{缓冲选择, x} 拼接寻址
wire wr_sel = ~pixel_y[0];    // 渲染进"不被显示"的那块
wire rd_sel =  pixel_y[0];
wire [9:0] next_y = (pixel_y == V_TOTAL-1) ? 0 : pixel_y + 1;
```

- 扫描第 Y 行时：显示缓冲读出 Y 行；渲染侧判定 **Y+1 行**并写入另一块。
- 一行 1650 个时钟，而渲染只需覆盖活动区 1280 列——时间余量极大。
- 从最后一条总行（y=749）回绕渲染第 0 行，保证首条可见行在垂直消隐期间就已备好。
- **16bit 行缓冲是刻意的**：2×2048×16 = 64 Kb ≈ 8 个 9Kb BRAM；存 888 要翻倍。
  展开放在显示侧用位复制完成（见第六节）。
- 踩坑：步长必须是 2048。最初声明 2×1280，`{sel, x[10:0]}` 的第 11 位被 x 占用，
  x>512 的写入串进另一个缓冲 → 条纹状砖块残影 + 照片模式背景损坏。

## 五、渲染侧（逐级解析）

### 5.1 命中判断——P2c 的两处关键改动

**改动一：y 命中整行寄存。** 一行之内 next_y 恒定，y 比较结果对 16 个槽都是常量，
没有任何理由每像素重算。实现：

```verilog
next_y_next = (pixel_x == H_TOTAL-1) ? inc(next_y_r) : next_y_r;   // 提前一拍
yhit_r[i]  <= (next_y_next >= s_y) && (next_y_next < s_yph);       // 每行算一次
hit[i]     = s_en && (pixel_x >= s_x) && (pixel_x < s_xpw) && yhit_r[i];
```

`next_y_r` 仅在行回绕周期自增、其余周期保持，与光栅严格锁步；复位值 1 对应
pixel_y=0 时的 next_y。逐像素热路径从此只剩 x 方向两次纯比较。

**改动二（反面教训，同样重要）：优先级选择保持朴素 for 循环。**

```verilog
for (k = NSLOT-1; k >= 0; k = k-1)
    if (hit[k]) begin found = 1; picked = spr_tab[k][23:0]; end
```

循环向上覆盖，**槽号最小者胜**。曾手工改写成"授权掩码 + OR 树"（grant[j] = hit[j]
&& 无更低槽命中），实测像素域**恶化 0.6 ns**（−0.080 违例）——TD 对朴素循环综合出的
结构已经最优。结论记入代码注释：不要替综合器做它已经做得更好的事。

### 5.2 三级取色优先

```
精灵(found) > 砖块(b_alive) > 瓦片(tile_rgb≠0) > 透明(16'h0000)
```

精灵压过砖块是玩法需要（球和挡板必须始终可见）。

### 5.3 砖块层——程序化生成，不占槽位

60 块砖若占精灵槽要用 60 个槽；实际按 10×6 网格、128×32 格**纯组合生成**：

```verilog
b_col = bdx[10:7];  b_row = bdy[9:5];                       // 128/32 均为 2 的幂
b_idx = {b_row,3'b0} + {b_row,1'b0} + b_col;                // row*10 = row*8+row*2
b_alive = 网格内 && b_idx<60 && brick_mask[b_idx];
```

* `row*10` 用移位加实现——直接 `×10` 曾被综合成 MULT18（8 级组合），把像素域从
  +0.6 拖到 −0.21（REPORT_MATERIALS 案例 7）。
* 颜色按行查表（红/橙/黄/绿/蓝/紫 6 行）。
* 整层成本约 50 LUT；开关状态就是外部那个 60 位 `brick_mask`。

### 5.4 RGB888 → RGB565 打包

```verilog
{c[23:19], c[15:10], c[7:3]}    // 各通道取高位，真转换
```

踩坑：早期直接取 24 位颜色的低 16 位，那不是转换（绿 0x20FF20 变成 0xFF20 = 黄）。

## 六、显示侧

```verilog
ovl_dout <= ovl[{rd_sel, pixel_x + 1}];   // 地址 +1，补偿 BRAM 一拍读延迟
ovl_rgb   = {d[15:11],d[15:13], d[10:5],d[10:9], d[4:0],d[4:2]};  // 位复制展开
rgb_out   = (ovl_dout != 16'h0000) ? ovl_rgb : bg_rgb;            // 0 = 透明
```

- 读地址取 **x+1**：BRAM 读延迟一拍，提前一列取数让数据恰好落在当前输出像素上。
- 565→888 用**位复制**（高位补齐）而非移位，免乘法。
- **16'h0000 = 透明**是全引擎的统一约定：精灵纯黑、瓦片 0、空行缓冲都汇到同一个
  判断 `ovl_dout != 0`。副作用：**画不出纯黑的精灵**（已知限制，见第九节）。
- 背景从最后一个 mux 口进入——照片、游戏纯黑、SD 故障品红都只是 bg_rgb 的不同来源。

## 七、槽位预算（两个游戏共用 16 槽）

| 槽 | 打砖块 | 侵略者 |
|---|---|---|
| 0 | 球 | 玩家飞船（无敌期按位闪烁 en） |
| 1 | 挡板 | 玩家子弹 |
| 2–7 | — | 敌机 6 架（颜色按队：红/橙/紫） |
| 8–10 | — | 血条 3 块 |
| 11–13 | 血条 3 块 | 空闲 |
| 14/15 | — | 敌弹 2 发；15 兼"游戏结束"横幅 |

"槽号小者胜"与预算天然吻合：玩家(0) > 子弹(1) > 敌机(2+) > 血条(8+) > 横幅(15)。

**写表协议与外部契约**：

* 写口由顶层三选一 mux 供给：清表扫描器（模式/游戏切换后连续扫 3000 拍把全表 en 清零）
  > 侵略者 > 打砖块。
* 打砖块在 `frame_tick`（y=720，垂直消隐起始）后的四级小流水里推槽——**在消隐期更新**
  是刻意的：曾在 y=0（第一条可见行）更新导致行缓冲半新半旧、挡板后拖尾影。
* 侵略者每时钟连续轮推 16 槽（每槽每 16 拍刷新一次），位置值只在 frame_tick 变化，
  60 fps 下槽间一拍的新旧差 ≤ 8 px，不可见。
* **负坐标不归引擎管**：侵略者从屏左滑入时由游戏侧裁剪后推入
  （`e_drawx = max(0,x)`、`e_draww = w+x`）——直接推负 X 曾造成"编队不可见但可被击杀"
  （REPORT_MATERIALS 案例 11）。
* 引擎内全部比较为无符号数，槽位坐标域为 0..2047 / 0..1023。

## 八、资源与时序账

| 项 | 数值 | 说明 |
|---|---|---|
| 行缓冲 BRAM | 2×2048×16 = 64 Kb ≈ 8 块 9Kb | 全片 27 块 BRAM 的大头 |
| 精灵表 | 16×67 bit | 分布式 RAM（LUTRAM），不占 BRAM |
| DSP | **0** | 全部移位/加法实现（含 row×10） |
| LUT | 引擎整体数百级 | P2c 后渲染路径不再是像素域最差路径 |

时序实测轨迹（像素域 SWNS，73.33 MHz）：

| 版本 | 结构 | 裕量 |
|---|---|---|
| v2（R85 基线） | 每像素 16×(2 次比较 + 2 次加法) + 优先级链 | +0.528 |
| P2 首版（否决） | 边界预计算 + grant 掩码 OR 树 | −0.080 ✗ |
| P2b（否决） | 边界预计算 + 原 for 循环 | +0.003（太薄）✗ |
| **P2c（采用）** | 边界预计算 + **y 命中整行寄存** | **+1.119**（当时）✗→✓ |
| R2 最终 | 同上（+ P1-R2 复位脉冲） | +0.722（域内最差路径已让位给侵略者帧逻辑） |

## 九、已知限制与决赛扩展点

1. **纯黑精灵不可画**：黑 = 透明约定所致。若决赛需要，可把行缓冲加一位
   "存在位"或将透明键值改为 16'hFFFF 类非常量。
2. **无负坐标**：引擎比较全为无符号；屏外滑入必须由游戏侧预裁剪。
3. **精灵是实心矩形**：无位图/旋转/缩放/逐像素 alpha。决赛"缩放引擎"的自然切入点：
   在渲染侧 hit 命中后、写行缓冲前插入采样级（行缓冲一帧的时间余量极大），
   表项位段需相应扩展（缩放参数、纹理基址）。
4. **槽位表每帧全量重推**：游戏侧职责，简化了引擎的脏标记/一致性逻辑。
   若槽位增多（如 >32），应考虑改为"变化时写"+ 帧序号校验。
