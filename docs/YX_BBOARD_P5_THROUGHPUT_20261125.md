# YX_BBOARD_P5_THROUGHPUT_20261125 — 以太网入口吞吐压力测试：设计的实时余量只有 0.85×？

## 0. 一句话结论

**设计的可持续入口吞吐 = 3.03 MB/s，而这套 720p 码流按 60fps 播放需要 3.58 MB/s
—— 只有 0.85 倍，也就是达不到实时。** 这与 TB 一直报的 `stall2=13%`（欠扫描）
是同一件事。

这个数此前**没有任何门禁能发现**：所有默认入口的 TB 都会等 FIFO 有空位才发包
（`while (eth_room < len+128) ...`），所以 `drop=0` / `bytes` 精确匹配只证明
"在 TB 配合的节奏下不丢包"。

---

## 1. 为什么默认门禁测不到

`tb_yxvp_bboard.v` 的发送进程：

```verilog
while (eth_room < (e_len + 128)) @(negedge gmii_clk);   // ← TB 自己刹车
e_send_pkt(e_off, e_len);
```

即 **TB 会一直等，直到 FIFO 有余量**。于是：

- `GATE-ETH ok=292 drop=0 bytes=297989` 精确匹配 ✔
- 但它只说明"设计消化多少，TB 就发多少"，**不说明设计能消化多少**。

## 2. 怎么测

TB 里已有 `+NOSTALL` 开关（`while (!nostall && ...)`），本轮补齐入口并修正测量：

| 项 | 做法 |
|---|---|
| 不节流 | `+NOSTALL`，按 TB 能达到的最快速度连发 292 个包 |
| 速率窗口 | ★ 在 `eth_tx_done` 那一刻**快照** `st_cyc_tx` / `st_byte_tx`，用发送窗口当分母 |
| 判据 | 压力模式**换**判据（`drop>0 && delivered>0`），默认入口的判据一个字没动 |

> ★ 为什么必须快照：TB 用约 50 万拍就把 292 个包发完了，而主流程要跑满 `wd`
> （数百万拍）。若用整段 `st_cyc` 当分母，后面无负载的空转期会把速率稀释十几倍。

---

## 3. ★ 三个数，只有第三个有意义

| 测法 | 数值 | 能不能当"余量"用 |
|---|---|---|
| 线速压力：提供 vs 消化 | 提供 59.3 MB/s → **丢 132/292 包（45%）**，交付 54% | ❌ 只说明"吃不下线速"（本来也不是需求） |
| 发送窗口平均（前 5.02 ms） | **30.9 MB/s** | ❌ **这是突发段**，不是持续能力 |
| **整段可持续（5 帧全消化）** | **3.03 MB/s** | ✔ **这个才是** |

### 3.1 为什么 30.9 MB/s 是个陷阱

设计消化的时间分布极不均匀。节流模式（TB 配合）下每 250k 拍的交付速率：

```
t=  500000  sent=155244   本段 +7972    3.19 MB/s
t=  750000  sent=155244   本段     0    0.00 MB/s   ← 开始停
t= 1750000  sent=155572   本段   328    0.13 MB/s
t= 2250000  sent=163639   本段  7411    2.96 MB/s
t= 2500000  sent=163639   本段     0    0.00 MB/s   ← 又停
t= 4000000  sent=182600   本段 18555    7.42 MB/s
t= 4250000  sent=286743   本段 104143  41.66 MB/s   ← 突发峰
t= 4500000  sent=286743   本段     0    0.00 MB/s   ← 长时间停
```

**前 5 ms 交付了 155244 字节（31 MB/s），随后停 10~35 ms 不动。**
所以"发送窗口平均"恰好落在突发段上，把它当余量会得出完全错误的结论。

### 3.2 真正的可持续速率：看帧完成时刻

```
FRAME #1 t=1599055   FRAME #2 t=3452830   FRAME #3 t=6301254
FRAME #4 t=7988709   FRAME #5 t=9841471
```

5 帧共 **9.84M 拍 = 98.4 ms**（clk100）。

```
设计可持续   = 297989 B / 0.0984 s = 3.03 MB/s
720p60 需求  = 59598 B/帧 × 60 fps = 3.58 MB/s
比值         = 0.85×
```

而 720p60 的 5 帧应该只用 5 × 16.67 = 83.3 ms，设计用了 98.4 ms，**慢 18%**。

这与 `stall2=1321372/9880863 (13%)` 完全吻合——显示侧有 13% 的时间在等数据。
单帧看也不均匀：帧 1/4/5 约 1.6~1.85M 拍（≈实时），帧 3 用了 2.85M 拍（1.7×）。

## 4. ★ 顺带抓到一个会破坏回归的编译错误

本轮改动**未提交前**，`bboard_key` / `bboard_sys`（不带 `BBOARD_ETH` 的入口）
**编译直接失败**：

```
tb\tb_yxvp_bboard.v:1096: error: Unable to bind wire/reg/memory `nostall' in `tb_yxvp_bboard'
2 error(s) during elaboration.
```

原因：`nostall` / `st_*` / `eth_*` / `e_npkt` / `slen` 全都声明在
`ifdef BBOARD_ETH`（139–325 行）内，而压力判据 `if (nostall)` 写在了 `endif` 之后。

**这个错只在非 ETH 入口暴露**，而 `eth_stress` 自己跑得好好的——正是"只跑新入口、
不跑老入口"会漏掉的典型。修法：

- 压力分支整体收回 `ifdef BBOARD_ETH` 内（`end else` 后接 `endif`）；
- 默认判据改为赋值给单一 `pfinal`，让 `TB-SUMMARY` 仍然只有一处，
  避免两条 `TB-SUMMARY` 互相覆盖（`run_sim` 取最后一条）。

修后两条编译路径都过：非 ETH（`bboard_key` 源单）与 ETH（`bboard_sys_eth` 源单）。

> 教训：**新增的可选模式必须把"关闭态"的老入口也跑一遍**。这个 bug 在
> `eth_stress` 上是零症状的。

## 5. 结论与可选方向

**设计当前达不到 720p60 实时**（0.85×）。是否要修，取决于目标帧率：

| 目标 | 需求 | 现状 | 结论 |
|---|---|---|---|
| 720p **30**fps | 1.79 MB/s | 3.03 MB/s | 1.7× 余量，够 |
| 720p **60**fps | 3.58 MB/s | 3.03 MB/s | **0.85×，不够** |

若必须 60fps，瓶颈在**管线的平均消化能力**，不在以太网入口（入口能吃 31 MB/s 突发）。
需要先定位是哪一级在停：`hdr_parse` 背压 → `ixdec` → `band` 渲染 → SDRAM 写带宽。
TB 已有的 `POLL` 行里 `band/fet/scan/ixwr/ctl` 各状态机字段足以进一步定位，
建议下一步做**逐级占空比统计**（每一级"在忙"的拍数占比），找出 13% 欠扫描的来源。

## 5A. ★ 逐级占空比定位（2026-11-25 续）——瓶颈是**上游解码**，不是渲染也不是取带

### 5A.1 两次走错的诊断（记录下来，避免重犯）

| 走错的判断 | 依据 | 为什么错 |
|---|---|---|
| "欠扫描 12% 期间 band 100% 在 st=1 → 在等取带" | 加了 `stall2 期间 band 状态分布`探针 | `stall2` 的定义就是 `pend_cnt==2`，而 `can_render = !frame_wait && (pend_cnt<2)` → 两者是**同义反复**，什么也没证明 |
| "真实流 `rd_bursts` 高 36% → `cp` 抢 RD2 使取带变慢" | 帧 5 `rd_b=17845` vs `13151` | 实测 `fetchwait` 两者几乎相同（差 576 拍），推断被否 |

> 教训：**探针本身必须先证伪**。若统计量与被解释量在定义上就等价，得到的"相关"
> 是恒等式，不是证据。

### 5A.2 完整周期会计（`yx_vp_band` 的 6 种拍子）

`st=1` 是多用途状态，必须拆开数：`!can_render`（背压）/ `can_render && !fetch_r`（发请求）
/ `can_render && fetch_r && !rd_dvld`（真等数据）。

| 项目 | 合成流 `bboard_key` | 真实流 `bboard_sys` | 差 |
|---|---|---|---|
| `tot` | 8,027,829 | 9,880,863 | +1.85M |
| `sdram_busy` | 5,133,310 (63%) | 5,884,007 (59%) | |
| **`idle`**（st=0 等帧） | 246,506 (3%) | **1,749,857 (17%)** | **+1.50M** |
| `backpressure`（等扫描端） | 1,032,354 (12%) | 1,382,613 (13%) | +0.35M |
| `issue`（发取数请求） | 288,900 (3%) | 288,900 (2%) | **0** |
| **`fetchwait`（真等数据）** | 1,276,069 (15%) | **1,275,493 (12%)** | **−576（0.05%）** |
| `book`（装载码本） | 288,000 (3%) | 288,000 (2%) | **0** |
| `write`（写 16 像素） | 4,608,000 (57%) | 4,608,000 (46%) | **0** |

自洽性可逐项验算：`write = 288,000 块 × 16 拍`、`book`/`issue`/未归类 st1 各 288,000
（= 每块 1 拍）—— 与代码完全对得上，探针可信。

### 5A.3 结论

```
渲染器忙时 ≈ 1.29M 拍/帧   <  实时预算 1.667M 拍/帧   → 渲染算力够
fetchwait 两流相同                                    → 取带延迟不是瓶颈
真实流多出的 1.50M 拍全部在 idle（等下一帧提交）        → 上游解码是瓶颈
```

**上游解码/提交路径交付一帧需要约 1.85M 拍（18.5 ms ≈ 54 fps），比 60 fps 慢 11%**，
于是渲染器每帧空等约 300k 拍。以太网入口无关（文件直推与网络送入选帧时刻完全相同）。

### 5A.4 下一步（未做）

对解码链（`yx_b_hdr_parse` → `yx_vp_ixdec` → `yx_b_ix_seq_wr` 的索引写 SDRAM →
`yx_vp_ixbuf` 交换）做同样的 6 项周期会计，定位这 11% 落在哪一段。
候选怀疑点：DELTA 帧的补丁解码是否串行、索引写与取带读的 SDRAM 仲裁、
`swap_done` 的提交是整帧屏障（一帧内无流水）。

## 5B. 解码链与 ixdec 状态分布（2026-11-25 续）——瓶颈是索引写的**延迟**，不是算力

### 5B.1 解码链占空比（band 在 st=0 等帧的那 1.75M 拍里）

```
ixdec_busy 93%   dec_nrdy 86%   hdr_nrdy 0%   ixwr_push 75%   ixwr_grp 21%   sdram 51%
```

`hdr_nrdy = 0` → **字节源从不阻塞**，入口方向彻底排除。

### 5B.2 ixdec 状态分布（占全部 9,880,863 拍）

```
S_WALK  = 7,798,428 (78%)   ← 全部卡在这里
S_KEY   =   405,545 ( 4%)   ← KEY 帧 57,600 字 × ~7 拍，对得上
S_WALKR =   172,800 ( 1%)
S_DIDX  =    13,176 ( 0%)   ← 4 个 DELTA 帧共 13,176 个变块
S_MAP   =    21,600 / S_FD = 5,458
```

### 5B.3 S_WALK 子情况拆分

```
walk_next=166,212(1%)  walk_didx=6,588(0%)  walk_wait=7,625,628(77%)  map1=7,652,690
```

`map_bite` 为 1 的总拍数 7,652,690 ≈ `walk_wait` —— 走查**卡在同一个变块上等了 7.6M 拍**，
不是"每个变块等 580 拍"。整个仿真只成功处理了 6,588 个变块（`DIDX = 2 × 6,588`，IDXB=2 ✓）。

### 5B.4 停滞成因拆分（`ix_rdy = ix_acc_phase && pf_room && !busy[act^1]`）

```
phase=6,228(0%)   pfroom=5,485,215(71%)   busy_other=2,132,447(27%)
```

**71% 是补丁 FIFO（8 深）满**，27% 是"渲染器正在渲染另一缓冲"。

### 5B.5 根因

`yx_b_ix_seq_wr.v` 的写协议是**严格单突发在途**：

```verilog
S_PUSH:    // 组内逐字推（1 字/拍）；推满 128 停推，等本组突发完成
S_GRPDONE: // 等本组突发落 SDRAM（组协议下严格单突发在途，事件唯一）
```

且 `wr_valid` 在 `PHY_COPY` 阶段归拷贝路径所有，补丁写不进去。

但**索引写总量只占约 6% 的周期**（拷贝 166k + 补丁 416k 字 = 582k 字 / 9.88M 拍），
写通路空闲 94%，`pf` 却满了 71% —— **不是吞吐问题，是突发性/延迟问题**：
8 深 FIFO 吸收不了"128 字突发 + 等落地 + 拷贝独占"这种锯齿。

> 教训（第三次踩）：**探针本身必须先证伪**。若统计量与被解释量在定义上等价
> （如 `stall2` 与 `can_render`），得到的"相关"是恒等式。

## 5C. 杠杆 A 试验：码本改 32 位（2 像素/拍）——性能达标，但触发了一个潜伏问题

### 5C.1 动机与做法

渲染器忙时 1.35M/帧（占 60fps 预算 81%），其中写行缓冲 0.92M（57,600 块 × 16 拍）是大头。
把 `book` 从 16 位/字改成 **32 位/字（一字装 2 像素）**，读一次出 2 像素 → **8 拍/块**：

| 位置 | 改动 |
|---|---|
| `book` | `[15:0] book [0:16*CBSIZE-1]` → `[31:0] book [0:8*CBSIZE-1]`（**总位数不变**，BRAM 数量不变） |
| `book_ra` | 14 → 13 位，初值 `{idx, 4'b0000}` → `{idx, 3'b000}` |
| 码本上传 | 半字写：`book_wa[0]` 选高/低半 |
| 写循环 | `st=3` 16 拍 → **8 拍** |
| 行缓冲写口 | `ln_we_r <= (st==3) && wp[0]` → 每拍都写；`ln_wd_r <= book_rdata`（已打包） |
| 位分配 | `q_row = wp[3:2]` → `wp[2:1]`；块内字号 `wp[1]` → `wp[0]` |
| `pix_hold` | 删除 |

**为什么不用"BRAM 双口读两个地址"**：`book` 需要 1 写口（上传）+ 2 读口（渲染）= 3 个访问，
而 `EG_LOGIC_BRAM` 只有 A/B 两口。改 32 位宽后仍只用 1 个读口。

**一个必须一起改的细节**：`q_row = wp[3:2]` 是靠 `wp` 数到 15 才能覆盖 4 行的；
改成 8 拍后若不动它，`wp[3:2]` 只能取到 0/1，**行 2、3 永远写不到**。

### 5C.2 结果：性能目标达成

| 指标 | 改前 | 改后 |
|---|---|---|
| `DUTY-BAND write` | 57% | **30%**（精确减半） |
| `DUTY tot` | 8,027,829 | **7,576,651**（−451k） |
| 行缓冲内容 | — | `golden=0 scan=0 igold=0 cperr=0` **全过** |
| 码本上传 | — | `BOOK[0..3]` 与新布局期望逐字匹配 |

### 5C.3 ★ 但门禁 FAIL：AXIS 流整体偏移 2 像素

```
axerr=3235351 (want 0)   ax_beats=3235351   ax_lines=2527（原 2728）
got[i] = exp[i+2]  逐项成立（均匀移位，非随机损坏）
```

**根因不在改动的模块里**，推理链：

1. AXIS 流不是从行缓冲来的，而是显示侧经 **RD1 从 SDRAM 帧缓冲**读的
   （`yx_b_scanout` → `yx_b_scanout_play` 的 `rd1_addr/rd1_load/rd1_len`）；
2. `golden=0` 证明 **SDRAM 内容对**、行缓冲也对；
3. 错误是均匀 2 像素移位，TB 的期望模型 `AX_OFF=0 / AX_SWAP=0` 无补偿偏移。

→ **数据全对，是 RD1 读的起点偏了 1 个字。** 该路径未被改动，
所以这是**被时序改动触发的潜伏问题**；它依赖 SDRAM 仲裁时序，
**在真实硬件上（仲裁时序与仿真不同）同样可能出现**。

**尚未确证**：怀疑 RD1 首个突发在仲裁延迟下丢失导致整行左移，但**没有证据**，
需加探针比对"RD1 请求地址 vs 返回数据"。

### 5C.4 处置

改动已回退，主干保持绿色。补丁存于
`docs/patches/p6a_book32.patch`（可重新应用）。**先修 RD1 对齐，再回来做杠杆 A**：
它是正确性问题且硬件可能复现，优先级高于性能；且门禁长期红着无法判断后续改动。

## 5D. ★ 最终结论（2026-11-26）：720p60 达标，且是两个真 bug 修好后的结果

### 5D.1 两个真 bug（都不是 TB 侧问题）

**Bug 1：`video_user`/`video_last` 与数据走不同深度的路径**

```verilog
// yx_b_scanout.v 改前
assign video_valid = vad[`VDLY] && armed_w;   // pa_w + 8 级
assign video_user  = vsrc_user_w && armed_w;  // 源相位 + 0 级  ← 深度差 8
```

根因：三个移位寄存器**输入深度不同**——`vad <= pa_w`（`O_pixel_active = S_active`，
源内 0 级），而 `vud <= vsrc_user_w` / `vld <= vsrc_last_w`（`O_video_user = Q_user`，
源内 2 级）。旧做法"保持源相位"让 user 的落点依赖 `armed_w`(=vb_seen，渲染侧信号)
→ **相位随码流漂移**。

修法：user/last 改取 `vud[VDLY-2]` / `vld[VDLY-2]`，与 valid 同源同机制。
验证：UVGAP 探针实测两流四帧全为"user 后第 0 拍出现首个 valid"。

**Bug 2：skid 清计数时未复位指针（长期潜伏，book32 才踩出来）**

```verilog
// yx_b_scanout_play.v 帧边界分支（!loaded / vb_start）改前
primed <= 1'b0;
sk_cnt <= 3'd0;            // ← 只清计数，sk_wp/sk_rp 沿用旧值
```

帧边界后：首次 push 写到**沿用的** `sk_wp`，首次 take 却从**陈旧的** `sk_rp` 读
→ 读到的不是刚推入的字 → **整帧前移 1 个字**。偏移量 = 边界时刻 `(sk_wp − sk_rp)`，
由预取节奏决定 → **随码流变化**。

修法：清 `sk_cnt` 时同时 `sk_wp <= 0; sk_rp <= 0;`。

> 为什么长期潜伏：只在预取节奏使 `sk_wp ≠ sk_rp` 时才暴露。book32 改变渲染时序
> → 改变 SDRAM 仲裁 → 改变预取节奏 → 踩出来。

### 5D.2 定位过程（每一步都靠可证伪的实验，且两次自我否证）

| 步骤 | 观察 | 结论 |
|---|---|---|
| RD1 首次 pop 探针 | 两流 `do` 都 == `mem[i_base]` | FIFO 侧正确 → 丢失点在 skid 消费侧 |
| FSTAT 帧首统计 | 两流均 `valid=921600 user=1`、帧首时刻逐帧相同 | 否掉"帧首相位"假设 |
| FSB 逐拍 dump | `key` 每拍不同、`sys` 前 12 拍全同（`f7f3ef`） | 解释"两流反转"假象：sys 对 1 字偏移不敏感 |
| 代码核对 | `sk_cnt` 清零但指针未复位 | **根因** |

**两次自我否证**（记录以免重犯）：
1. 第一版探针统计"`stall2` 期间 band 在哪个状态"，得出"100% 在 st=1"→ 误判为
   "在等取带"。但 `stall2` 的定义就是 `pend_cnt==2`，而 `can_render=(pend_cnt<2)`，
   两者是**同义反复**，什么也没证明。
2. 由真实流 `rd_bursts` 高 36% 推断"`cp` 抢 RD2 使取带变慢"。实测 `fetchwait`
   两流差仅 576 拍，推断被否。

> 教训：**探针本身必须先证伪**。若统计量与被解释量在定义上等价，得到的"相关"
> 是恒等式，不是证据。

### 5D.3 判据收紧：删掉相位常量

`AX_OFF` / `AX_SWAP` 是 TB 侧"管线相位校准常量"，长期用来补偿 user/last 与数据的
错位。两个 bug 修好后 **`AX_OFF=0` 下合成流与真实流同时 `ax_errs=0`** → 常量已删除。

保留它们只会掩盖同类结构缺陷：实测 book32 后同一常量只能修好一个流，造成"两流
反转"的假象，浪费了多轮排查。**判据里现在不含任何可调相位项。**

## 5E. TD 布局布线复跑（2026-11-26）——P&R 收敛确认

book32 改了 band 的写节奏、skid 复位改了 scanout 行为，两者都在 100M 域，
必须确认 P&R 后仍收敛。非工程流到 route（`out/p5td/p5_pr2.tcl`，双 bit 预检）：

| 指标 | 基线 `0ecdea5` | book32 后 `dcc4a75` | 结论 |
|---|---|---|---|
| `SWNS` / `STNS` | 0.000 / 0.000 ns | **0.000 / 0.000 ns** | 无新增 setup 违例 |
| `HWNS` / `HTNS` | −2.564 / −23.738 ns | **−2.564 / −23.738 ns** | **逐位相同** |
| 负 slack 条数 | 10 | **10** | 全部 `eth_rxd[0..3]`+`eth_rxdv` |
| `#lut` | 4279 (21.83%) | **4268 (21.78%)** | −11 |
| `#bram` / `#bram32k` | 53 / 64 · 10 / 16 | **53 / 64 · 10 / 16** | **不变** |
| `#IO` / `#pad` | 19 / 23 | 19 / 23 | 不变 |
| `#pll` / `#gclk` | 2 / 4 · 6 / 16 | 2 / 4 · 6 / 16 | 不变 |
| `BIT-8123`（未约束 IO） | 无 | 无 | — |

三点值得单独记录：

1. **`#bram` 仍是 53** —— 直接验证了"16,384×16b → 8,192×32b **总位数不变**"这个设计
   前提：TD 没有因位宽变化而改变映射方式。这是 book32 方案成立的关键假设。
2. **`HWNS`/`HTNS` 逐位相同** —— `eth_rxd` 那组 hold 路径的布局完全没动，

3. **负 slack 清单完全一致** —— 只有已知的 RGMII 输入 hold（§3.1 的判据/拓扑冲突，
   已决策不修），没有新增端点。

→ **P&R 收敛，改动无时序代价。** 唯一遗留的违例仍是那条已知的 RGMII hold。

## 5F. 真实 VQ-1024 码流验证（2026-11-26）——60fps 不只对测试流成立

### 5F.1 为什么必须补这一项

`docs/YXVP_VQ_DESIGN.md`（本轮入库）写着"720p VQ-1024 @24 fps 需要 2.76 MB/s"，
反推该码流约 **115 KB/帧**；而此前所有门禁使用的 `out/vp_720_5f.yxv2` 是
**59.6 KB/帧**——只有一半。所以"720p60 达标"当时仅在测试流上成立，真实码流的
解码量（补丁数）更大，未验证。

### 5F.2 做法

取 `out/xinji_720p24.yxv2`（15,054,178 B，1280×720@24fps，约 131 帧 → 114,917 B/帧，
与文档吻合），截前 600 KB 跑一次 `bboard_sys`。

> 这是**探索性测量**，不是门禁：截断流末帧不完整、且未喂 `gen_golden.py` 金标，
> 门禁项预期为红。只取 `FRAME` 完成时刻。

### 5F.3 结果：三条不同码率的流给出**逐位相同**的帧时刻

| 码流 | 字节/帧 | 帧 #3 | 帧 #4 | 帧 #5 |
|---|---|---|---|---|
| `vp_720_5f`（测试流，KEY+DELTA） | 59,598 | 4,162,272 | 5,849,727 | 7,537,182 |
| `vp_720_key`（全 KEY） | 121,762 | 4,162,272 | 5,849,727 | 7,537,182 |
| **`xinji_720p24`（真实 VQ-1024）** | **114,917** | **4,162,272** | **5,849,727** | **7,537,182** |

稳态帧周期 **1.687M 拍 = 16.87 ms ≈ vsync 16.67 ms**，三条流一致 → 都是**扫描端定速**。

余量（`stall2` 逐帧增量，真实码流）：0 / 5.7k / 650k / 801k / 801k / 293k
→ 稳态背压约 **800k/1.687M = 47%**（测试流 36%）。**渲染器有 47% 时间在等扫描端**，
说明真实码流下的解码压力完全被吸收。

### 5F.4 结论

**720p@60 在真实 VQ-1024 码流上同样达标**，不只是对 59.6 KB/帧的测试流成立。
码率从 59.6 KB/帧 提到 115 KB/帧（近 2×），帧周期没有任何变化。
