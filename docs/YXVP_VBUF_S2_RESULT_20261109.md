## 2. 验证结果

### KEY-only 流（40 帧，全 KEY）
```
CNT: emit=1474560 load=1474560 push=1474560 fpop=1474560 sdram=1474560
TB-SUMMARY: ALL PASS (frames=40, 7455737 clk)
```
**全链路逐位通过**：40 帧 × 36,864 像素全部经 解码器→skid FIFO→三缓冲→SDRAM→显示模型，零失配、零撕裂（写口永不触碰 ACTIVE 槽）、零乱序（显示帧号单调）。

### 背压行为验证
- SDRAM 模型写口 1/3 拍节流（≈49 MB/s 悲观假设）+ 每 8192 拍刷新停摆 64 拍：KEY 帧写入自动摊平到扫描帧槽内（pix_rdy 反压生效，解码停顿 177 万拍被正确吸收）。
- 解码核 32 深 skid FIFO：块内 16 像素突发绝不暂停（查表流水 2 拍配对，拍级暂停会错位一格产生棋盘格坏点——已复现并修复）。

### DELTA 流：发现架构级冲突
DELTA 帧全错且**按槽位分布**（slot 0 的帧误差小、slot 1/2 的帧近乎全错）。

**根因**：三槽各自持有独立快照。DELTA 语义要求未变块继承**上一帧**，但旋转槽里该块的内容是**上上帧**（N-3 帧时代）的。旋转帧槽与 P 帧差分在架构上互斥。

## 4. 架构决策点（需要拍板）

DELTA 视频与旋转 RGB565 帧槽互斥。三个出路：

### 方案 A：索引帧缓冲 + 条带渲染（推荐）
- **帧缓冲存索引不存像素**：720p 索引缓冲 57,600×2B = 115 KB（双缓冲 ×2 = 230 KB，1080p 460 KB）。
- DELTA 解码只写变化索引（几 KB/帧）；换帧时顺序拷贝 115 KB（≈2.8 MB/s @24fps，可忽略）。
- 显示端条带渲染器：每次预取 4 行块的索引 + 码本查表（码本 32 KB 全在 BRAM），渲染 10 KB 行带进 ping-pong 行缓冲，扫描期消化。
- **SDRAM 总流量 ≈31 MB/s**（索引扫描 27 + 拷贝 2.8 + 音频），比 RGB565 方案（≈190 MB/s）**省 6 倍**——100 MHz 甚至 75 MHz SDRAM 即可，1080p@24 也宽裕。
- 解码器大幅简化：发射 1 字/变化块（无 16 像素展开、无查表流水、无 skid 复杂度）。
- 索引级撕裂用双索引缓冲 + 拷贝-补丁-翻转消除。

### 方案 B：参考拷贝重建
DELTA 解码前把上一帧整帧拷贝到目标槽（720p 1.8 MB/帧 → 剩余带宽下 ≈57 ms ✗ 超帧预算）。不可行。

### 方案 C：RGB565 槽 + KEY-only
保留现架构，视频全 KEY 编码（720p@24 VQ-1024 全帧 2.76 MB/s，25 MHz SPI 下 99% 占用 ✗ 仅 12.5 MHz 不可行）。浪费差分成果，仅作保底。

## 5. 下一步
