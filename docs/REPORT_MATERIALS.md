## 一、项目一句话

**在 19.6K LUT 的国产 FPGA（安路 EG4S20）上，构建一个"可重构图形平台"：同一套像素通路，通过模式切换承载照片浏览与两款 8-bit 游戏；游戏机只是它的第一个应用。**

硬件平台：**AC201 评估底板 + AC601-EG4S20 核心板**（第三方板，非官方 HX4S20C），核心器件 EG4S20BG256（19,600 LUT）、板载 SDRAM 2M×32（8MB）、QSPI 配置 Flash 16MB、50MHz 晶振、HDMI 输出。

## 二、系统架构

### 2.1 三层结构

```
┌─────────────────── 应用层 ───────────────────┐
│  照片浏览器            打砖块        太空侵略者 v3 │
│  8 张 BMP / 轮播     10×6 砖     3队×2架/无限波次 │
└───────────────┬──────────────┬───────────────┘
                │              │
┌───────────────▼──────────────▼───────────────┐
│                 图形层（自研精灵引擎）          │
│  16 槽精灵 · 逐像素优先级 · 行缓冲双端口 BRAM   │
│  图层优先级：精灵 > 砖块/图块 > 照片背景        │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│                  媒体层                       │
│  SD/SPI → BMP 解析 → BGR888→RGB565 → SDRAM    │
│  SDRAM 暂存区：WR2 写 / RD2 读（双端口）        │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│                  平台层                       │
│  HDMI 720p59.3Hz TMDS 直驱 · 48kHz 音频 · OSD │
│  模式切换：SW7（照片/游戏）· SW6（打砖块/侵略者）│
└──────────────────────────────────────────────┘
```

### 2.2 时钟方案

| 域 | 频率 | 用途 | 实测裕量 |
|---|---|---|---|
| sys_clk_50m | 50 MHz | SD/SPI、按键、加载器、游戏逻辑 | **+0.843 ns** |
| SDRAM 控制器 | 100 MHz | 4 端口 SDRAM（RD1/RD2/WR1/WR2） | **+2.459 ns** |
| HDMI 像素域 | 73.33 MHz | 像素通路、精灵、淡入淡出 | **+0.528 ns** |
| HDMI 串行域 | 366.67 MHz | TMDS 编码 | **+0.821 ns** |
| TMDS 跨域（厂商 PHY） | — | 差分输出 | −0.649 ns（厂商固定违例） |

分辨率 1280×720，HTOTAL 1650 / VTOTAL 750 → 刷新率 **73.33MHz ÷ 1237500 = 59.3 Hz**。

### 2.3 为什么不用现成的双缓冲 framebuffer

设计要求"换图时**立刻呈现**新内容"，而双缓冲需要"写满一整帧 → 翻转"：

- 一帧 460,800 字（1280×720×RGB565/2），写满约需 4 秒，期间旧画面继续显示
- 我们的方案改为**单缓冲 + 逐像素回放**：图片加载时直接覆盖正在显示的缓冲，
  画面会"从上到下刷出来"，再用 **4 秒淡入淡出**遮住刷新过程
- 代价：需要接受"加载期间画面不完整"；收益：换图延迟从 4 秒降到 0

## 三、关键设计

### 3.1 SD 卡启动可靠性（三机制）

SD 卡（SanDisk Ultra 32GB）在 FPGA 上电时的初始化极不稳定，我们踩了三天，最终归纳为三个机制：

| 机制 | 实现 | 解决的问题 |
|---|---|---|
| **上电静默** | 上电后 2 秒内 CS 保持高、**不输出任何时钟** | 卡还没准备好接收命令就发时钟 → 卡进入异常状态 |
| **时钟冲刷** | 释放复位前先发 **65,536 个时钟**（约 160ms @400kHz） | 把卡从上一次（FPGA 重配置前的）中断事务中"推"出干净状态 |
| **周期重试** | 初始化失败每 **5 秒**重试一次；40 秒仍失败才显示品红 | 单次失败不影响整体，给卡自我恢复的机会 |

SPI 时钟：初始化 **400 kHz**，数据传输 **6.25 MHz**（实测 8.33MHz 偶发失败、12.5MHz 必然中途失败，6.25 是稳定上限，对应 **0.7 MB/s**）。

### 3.2 音频链路：与官方 IP 同架构，只换音源

官方例程（lab_ex_5）的音频通路是：

```
PLL3(12.288MHz) → 测试音发生器 → I2S_receiver（解串 24bit PCM）
              → audio_arc_calculate（N=6144，CTS 动态算）
              → HDMI 1.4b IP（消隐期数据岛打包）→ TMDS
```

我们的做法**完全保留后半段**（I2S 接收、ACR 计算、HDMI IP 的音频打包），只把"固定测试音"替换为 **PSG 事件音效发生器**：

- 48 kHz 采样率（由 73.33MHz 像素时钟分频，与视频同源 → 天生同步、零漂移）
- 4 种事件音：撞砖 880Hz、撞板 440Hz、失败 220Hz、通关 1320Hz
- 幅度 ±0x200000（约 −12 dBFS），不需要乘法器（用位移累加）

**这是可以写进报告的架构优势**：音频不是"另搞一套"，而是在官方架构上做应用层增强。

### 3.3 精灵引擎（行缓冲架构）

| 参数 | 规格 |
|---|---|
| 精灵槽 | 16 个（每槽：使能、X/Y、宽高、颜色、优先级） |
| 存储 | 双端口 BRAM，2 × 2048 × 16bit RGB565 |
| 更新 | 每帧逐槽写入，游戏逻辑只改"槽位表" |
| 合成 | 每像素时钟按优先级选择图层，零 CPU 参与 |
| 特殊能力 | 负坐标裁剪（从屏幕外滑入）、文字/血条复用同一引擎 |

### 3.4 太空侵略者 v3（R85 新设计）

| 队 | 颜色 | 数量 | 速度 | 开火间隔 |
|---|---|---|---|---|
| 1 | 红 | 2 架 | 2 px/帧 | 90 帧起 |
| 2 | 橙 | 2 架 | 3 px/帧 | 70 帧起 |
| 3 | 紫 | 2 架 | 4 px/帧 | 50 帧起 |

- 三队**分批入场**（间隔约 3 秒），各自从左缘滑入 → 横穿 → 从右缘回绕
- **无限波次**：6 架清完进入下一波，全体提速（每波 +1 px/帧）、开火加密（每波 −8 帧）
- **敌机反击**：每队独立开火计时，从该队屏幕上最右的活敌机发射，最多 2 发同时在屏
- **3 条命**：受击后 90 帧（1.5 秒）无敌闪烁；屏幕左下角血条 3 个红块
- 数码管：左 4 格波数、右 3 格剩命
- 玩家子弹 12 px/帧（由 8 提升，飞行时间 0.6 秒，瞄准更跟手）

### 3.5 视觉特性

| 特性 | 实现 | 资源代价 |
|---|---|---|
| 淡入淡出转场 | 逐通道饱和减法 `pixel − dark`，25ms 一步 | 3 级流水，**DSP 0** |
| 亮度调节（SW0） | 与淡化合并为一次饱和加法 `pixel − dark + 24` | 0 |
| 对比度（SW1） | 移位加法 ×1.5：`v + v>>1` | 0 |
| 加载跑马灯 | 数码管逐位点亮 | 0 |

## 六、调试案例（报告"问题与解决"素材，共 12 例）

### 案例 1：WR2 端口永远不被服务
**现象**：图片能读卡但屏幕全黑。
**原因**：`rWR2_LENGTH` 为 0——LOAD 脉冲发在 SDRAM 控制器仍在复位期间，被丢弃。
**解决**：加载器启动后延时 8 拍再发 LOAD，并在端口配置完成前丢弃输入字节。

### 案例 2：RD1 抢占导致写端口饿死
**现象**：加载速度忽快忽慢，偶尔一张图卡住。
**原因**：仲裁优先级 RD1 > RD2 > WR1 > WR2，空闲的 RD1 仍以最高优先级占带宽。
**解决**：屏蔽未使用的 RD1/WR1，只保留 WR2/RD2。

### 案例 3：假时序违例 −10.26 ns
**现象**：报告显示 TMDS 跨域 −10 ns，但画面完全正常。
**原因**：厂商 PHY 内部的跨时钟路径未被正确约束，工具按错误周期计算。
**解决**：确认为厂商固定现象，不再追；改为盯住**像素域**裕量（真正的瓶颈）。

### 案例 4：偶发横向抖动
**现象**：画面每隔几十秒抖一下。
**原因**：读指针在 FIFO 空时被跳过一拍，导致整行错位 2 像素。
**解决**：读使能**绝不跳过**：FIFO 空时只保持旧数据，指针照常推进。

### 案例 5：SD 卡初始化不稳定
见 3.1 的三个机制。

### 案例 6：行缓冲越界
**现象**：某些精灵最右侧 1 像素串色。
**原因**：行缓冲写入未做右边界裁剪。
**解决**：按 `min(width, 2048 − x)` 裁剪。

### 案例 7：游戏碰撞的除法器拖垮时序
**现象**：加砖块碰撞后像素域从 +0.6 变 −0.21。
**原因**：砖块索引 `b_row × 10` 被综合成 MULT18（8 级组合）。
**解决**：改为 `{brow,3'b0} + {brow,1'b0} + bcol` 移位加法，裕量回到 +0.64。

### 案例 8：游戏切换互相污染
**现象**：切换游戏后旧精灵残留、挡板卡死。
**原因**：精灵推送未受使能控制，暂停时仍在写表。
**解决**：`spr_we <= enable`，并在模式切换时执行 3000 拍全表清零。

### 案例 9：转场期间按键丢失
**现象**：淡入淡出时按键不跟手。
**解决**：`load_idx` 自动同步（`img_idx != load_idx` 时立刻跟随），把按键排队。

### 案例 10：淡入淡出的颜色串扰
**现象**：转场时画面发绿。
**原因**：`{r8,g8,b8} >> shift` 把三个通道一起移位，低位互相窜入。
**解决**：逐通道独立移位。

### 案例 11（R85）：侵略者"打中没反应 / 打 A 死 B"
**现象**：命中判定与视觉不一致。
**原因**：渲染用**回绕后的 11 位无符号 X**，碰撞用**真实坐标**；编队负坐标时整队不可见但能被杀死。
**解决**：渲染改用带符号真实坐标 + 左缘裁剪；敌机子弹加"必须在屏内"门控。

### 案例 12（R85）：同源不同版的怪现象
**现象**：改一个常数，时序数字完全不变，但不良率不同。
**原因**：**TD 布局是确定性的**——网表结构不变则布局完全相同；只有**结构性改动**（加寄存器、改位宽）才会重抽布局。
**启示**：这也是为什么本项目出现"连续多次编译都起不来"——不是随机，而是同一个坏布局在重复。

## 七、视频播放功能（进行中，技术路线已验证）

赛题一的主题是"音视频播放系统"，我们在 R85 之后启动了视频播放功能，**已验证的部分**：

| 环节 | 状态 | 证据 |
|---|---|---|
| 视频容器 `.yxv` + PC 生成工具 | ✅ | 电脑端解码验证 |
| SD 读取 4.15MB / 8101 扇区 | ✅ | 串口回读 `YXV1` + 320×180 |
| 卡上文件绝对 LBA = 75968 | ✅ | 串口实测（含 2048 分区偏移） |
| 加载触发 / 基地址锁存 / 扇区数动态切换 | ✅ | LED + 串口计数器 |
| 320×180 窗口显示通路 | ✅ | 测试图案呈规则渐变 |
| **整帧画面正确显示** | ❌ | 待解决 |

**期间修复的 4 个真实 bug**（都可写进报告的"问题与解决"）：

1. `video_done` 被开机轮播的**照片加载**误置位 → 视频加载被永久抑制
2. 探针里 `sector_count × 512` 用了 **16 位乘法** → `8101×512` 溢出成 18,944，只读 37 个扇区就"完成"
3. 加载器的 `wr2_addr` 用**实时** `i_base` 而非锁存值 → 加载中途拨开关会把帧写劈成两半
4. `.yxv` 头实际 20 字节、固件按 16 字节跳过 → 每个字错位一个字

**结论**：SPI 带宽（0.7 MB/s）决定"实时流播"不可能（640×480@15fps 需 13.8 MB/s），必须"SDRAM 缓冲 + 播放"；8MB SDRAM 可存 36 帧 320×180（2.4 秒）。这条路线已走通 80%，剩余问题定位在 raw 字节拼装环节，已有完整存档（`src_VIDEO_WIP4`）。

## 八、已知限制

1. **换图加载 4 秒**：受 SPI 6.25MHz 上限限制（8.33MHz 偶发失败）
2. **TMDS 固定 −0.65ns 违例**：厂商 PHY 固有，偶发 1~2 像素噪点
3. **布局不确定**：LUT > 44% 时约一半编译会抽到"SD 初始化失败"的坏布局，需重抽
4. **视频未完成**：见第七节
5. **缩放未在 FPGA 内实现**：扩展要求 ③ 目前靠 PC 预处理

## 十、报告写作建议

### 10.1 建议强调的三个差异点

1. **"可重构"不是口号**：同一套像素通路 + 精灵引擎，承载了照片浏览和两款游戏；游戏只是第一个应用，决赛将换成自研 CPU + 卡带
2. **音频是与官方 IP 同架构的增强**，不是另起炉灶（保留 I2S 接收、ACR、HDMI 数据岛打包，只替换音源）
3. **指标全线超标**：分辨率 2.25×、帧率 3.95×，且 DSP 使用为 0（纯组合逻辑调优）

### 10.2 评委可能追问的问题（附答案要点）

| 问题 | 答案要点 |
|---|---|
| 为什么不用双缓冲？ | 换图延迟 4 秒 vs 0；用淡入淡出遮住刷新过程；SDRAM 端口只有 4 个，双缓冲会饿死写口 |
| 音频怎么保证同步？ | 48kHz 由像素时钟分频，与 TMDS 同源，ACR 参数 N=6144 |
| 精灵引擎和普通像素混合的区别？ | 16 个独立槽位 + 逐像素优先级 + 负坐标裁剪，游戏逻辑只改槽表 |
| 为什么 DSP 是 0？ | 乘法器会引入 8 级组合路径，把像素域从 +0.6 拉到 −0.2；全部换移位加法 |
| 视频为什么没做完？ | SPI 带宽物理上限 0.7MB/s；已打通缓冲+窗口显示，剩字节拼装；给出定量分析而非"来不及" |
| 为什么选 720p 而不是 640×480？ | 官方要求是"≥640×480"，720p 是 2.25 倍余量；且 HDMI 720p 是标准模式，EDID 兼容性最好 |

1. **自研 8-bit CPU**（卡带游戏机）：指令集、寄存器堆、取指/执行状态机
2. **卡带协议**：SD 卡上以文件为单位装载游戏，运行时按需读取
3. **精灵引擎深化**：缩放、翻转、旋转（90° 步进）、透明度混合、动画帧
4. **视频背景层**：完成 raw 拼装，把视频作为第 0 层
5. **音频频谱可视化**：FFT 或滤波器组，补上扩展要求 ⑤
