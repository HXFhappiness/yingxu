## 2. YXV2 格式（RTL 解码友好设计）

在 v0 的 20B 头 + codebook 之后逐帧：

```
帧头 5B: kind u8 | changed u24 LE | rsv u8     kind: 0=KEY 1=DELTA
KEY   : nb * idx_bytes                          光栅序全帧索引
DELTA : bitmap (nb+7)/8 B                       bit b = 块 b 变化；字节内 MSB-first
        + changed * idx_bytes                   光栅序仅变化块索引
idx_bytes: 1 (cb<=256) / 2 LE (cb=1024)
```

u24 而非 u16 的原因：1080p 单帧 129,600 块 > 65,535，KEY 帧的 changed 字段需要装下全帧块数。

解码器（= 未来 YX-VP-VQ RTL）流式模型：
- KEY：块计数器 0..nb-1 逐块取索引写帧缓冲
- DELTA：bitmap 先收进 BRAM（720p 仅 7.2 KB），随后按块号 b 流式走：map bit=1 取下一索引写帧缓冲，=0 保留上帧块。**无需随机访问，无需帧间回写。**

## 3. 真实码率实测（xinji_src.mp4，607 帧取前 300 帧）

测试素材是蒙太奇类内容（300 帧里 23~24 次硬切，平均 13 帧一切），**比典型演示视频更严苛**。

| 档位 | 全帧 | 差分平均 | P95 | 最差 DELTA 帧 | 25 MHz SPI（2.8 MB/s） |
|---|---|---|---|---|---|
| 720p@24 VQ-1024（主档） | 2.76 | **1.20** | 2.22 | **2.37** | ✓ 全帧不超 |
| 720p@30 VQ-256 | 1.73 | **0.71** | 1.34 | **1.43** | ✓ |
| 1080p@24 VQ-256 | 3.11 | **1.38** | 2.49 | 2.86 | 平均✓ 切镜头瞬超 2% |
| 1080p@24 VQ-1024 | 6.22 | 2.76 | 4.98 | 5.36 | 平均✓（99% 占用）切镜头✗ 不推荐 |

变化率分布（720p@24，DELTA 帧）：P25 14.0% / P50 27.4% / P75 42.3% / P95 74.1%。
静态镜头低至 0.4~1%（~0.2 MB/s），运动镜头 8~13%，硬切帧 >99%。

## 4. 结论

1. **720p@24 VQ-1024 主档确认**：最差帧 2.37 MB/s 也压得进 25 MHz SPI 预算（2.8），且留 15% 余量给协议开销。差分把码率砍掉 2.3×。
2. **1080p@24 VQ-256 可行，条件是帧缓冲平滑**：平均 1.38 MB/s 只有 49% 占用；切镜头 KEY 帧瞬时 2.86 略超，但切点在文件级已知，可预读（解码器三缓冲吸收）。这是经典 VBV 思路。
3. **1080p@24 VQ-1024 不推荐**：平均已 99% 占用，无任何余量。
4. 差分编码**零额外损失**：解码器帧缓冲里存的就是全帧 VQ 同一批索引（编码器对原始帧独立算索引，DELTA 只省传输），PSNR 与全帧 VQ 完全一致。实测 720p@24 VQ-1024：**PSNR 28.41 dB / Y-PSNR 29.46 dB**（vs RGB565 量化原图），与 v0 全帧同档。
5. 交叉验证：编码器输出的文件有效码率 1.20 MB/s == 测量脚本 1.20 MB/s；300 帧解码 bitmap/changed 一致性断言零失败。

## 5. 与 SD 升级的衔接

YXSD v2 快速引擎（25 MHz CMD18 实测 3.05 MB/s 纯数据相位）→ 主档 720p@24 差分 1.20 MB/s = **40% 占用**，剩余带宽足够音频立体声 44.1k（0.18 MB/s）+ 文件系统开销 + 预读平滑。1080p@24 VQ-256 平均 1.38 MB/s = 45% 占用，同样成立。
